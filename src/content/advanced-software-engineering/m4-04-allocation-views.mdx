# Allocation Views: Deployment, Install and Work Assignment

Module views show the code; C&C views show the running system. <Term id="allocation-view">Allocation views</Term> connect the software to **things that aren't software**: CPUs, file systems, networks, and the people who build it.

## What allocation views are

Allocation structures embody decisions about how the system relates to non-software structures in its environment. They show the relationship between software elements and elements of one or more external environments where the software is created and runs.

Questions they answer:

- What processor does each software element run on?
- In which directories is each element stored during development, testing and system building?

The style is defined by:

- **Elements:** a *software element* and an *environmental element*. A software element has properties it **requires** from the environment (e.g. 2 GB of memory); an environmental element has properties it **provides** to the software (e.g. 8 GB of memory).
- **Relation:** *allocated-to*. A software element is mapped (allocated) to an environmental element.

The software elements can come from either a <Term id="module-view">module view</Term> or a C&C view. There are three common allocation styles:

| Style | Maps | onto |
| --- | --- | --- |
| <Term id="deployment-style">Deployment</Term> | runtime components and connectors (C&C) | hardware of the computing platform |
| <Term id="install-style">Install</Term> | runtime components (C&C) | files and folders in the production environment |
| <Term id="work-assignment-style">Work assignment</Term> | modules (module view) | teams and people who build them |

## The deployment style

The deployment style maps components and connectors to the hardware they run on.

- **Software elements:** from a C&C view.
- **Environmental elements:** computers, devices, networks.
- **Used for:** **performance** (put components that talk a lot on the same machine or a fast link) and **availability** (put replicas on different machines).

An <Term id="artifact">artifact</Term> is a physical file produced by development, such as a `.jar` or `.ear` archive.

UML can also nest nodes, one inside another. The lecture's second example has four levels: a `«device» Sun Fire X4150 Server` → its `«OS» SUSE Linux Enterprise 10` → a `«JSP server» Apache Tomcat Server 5.5` → the deployed `«web archive» shopping.war`.

**Can a deployment view help with memory capacity analysis?** Yes, if you record the right properties: properties of the physical units (how much memory each machine *provides*) and properties of the software elements (how much each component *requires*). Add up what's allocated to each machine and compare.

## The install style

The install style allocates components of a C&C view to a **file management system** in the production environment.

Once the system is built, its files have to be packaged and installed on the target platform (a desktop computer, or a server running an application server). These files include libraries, executables, data files, log files, configuration and version-control files, license files, help files, deployment descriptors, scripts, and static content such as HTML files and images.

Any install-view notation must show:

- the **components**,
- the **files and folders**,
- the **mapping** between them,
- and the **tree structure** of the files and folders.

## The work assignment style

The work assignment style allocates **modules** to the **groups and individuals** responsible for building the system. It defines who implements and integrates each module.

- **Software elements:** modules. The lecture asks "modules or components?": the answer is modules, because teams write *code*, and code is organized as modules.
- **Environmental elements:** organizational units (teams, contractors, people).

The lecture's example is a table for a satellite ground system:

| Segment | Subsystem | Organizational unit |
| --- | --- | --- |
| Science Data Processing (SDPS) | Client | Science team |
| | Interoperability | Prime contractor team 1 |
| | Ingest | Prime contractor team 2 |
| | Data Management / Processing / Server | Data team |
| | Planning | Orbital vehicle team |
| Flight Operations (FOS) | Planning and Scheduling | Orbital vehicle team |
| | Data Management | Database team |
| | User Interface | User interface team |

<Callout tone="violet" label="Why work assignment is architecture">
Teams build systems that mirror their communication structure. If two modules that must talk constantly are given to two teams that never meet, the interface between them will suffer. The [Single Responsibility Principle](/courses/advanced-software-engineering/design-principles-and-srp#responsibility--actor) makes the same point at class level: one module, one actor.
</Callout>

<Callout tone="orange" label="Common mistake">
Mixing up deployment and install views. Deployment maps running components to *hardware*; install maps them to *files and folders*. And work assignment maps *modules*, not components, to teams, because teams write code.
</Callout>
