# Module Views: Decomposition and Uses

A <Term id="module-view">module view</Term> shows the system as **units of implementation**: subsystems, packages, classes. It's the view developers live in.

## What module structures answer

- What is the main functional responsibility of each module?
- What other software elements is a module **allowed** to use?
- What other software does a module actually use or depend on?
- Which modules are related by generalization or specialization (is-a)?

**How do they help?** Mainly with **modifiability**: if you know how responsibilities are split and who depends on whom, you can predict what a change will touch.

Four useful module styles:

| Style | Relation it shows |
| --- | --- |
| <Term id="decomposition-style">Decomposition</Term> | is-part-of |
| <Term id="uses-style">Uses</Term> | uses (depends on) |
| <Term id="generalization-style">Generalization</Term> | is-a (inheritance) |
| <Term id="data-model-style">Data model</Term> | relationships between data entities |

This lesson covers the first two, which the lecture works through in detail.

## The decomposition style

The decomposition style breaks a system into units of implementation. A decomposition view shows **how the code is organized into modules and sub-modules**, and how the system's responsibilities are split among them.

- **Relation:** is-part-of
- **Elements:** modules (subsystem, package, class, …)
- **Constraints:**
  - no loops are allowed in the decomposition graph;
  - a module can have only one parent.

Those two constraints make every decomposition a **tree**.

## The uses style

> A module **uses** another module if its correctness depends on the correctness of the other.

The uses view makes explicit which modules use which others to do their jobs.

- **Relation:** uses (depends on)
- **Elements:** modules
- **What it's for:** planning **incremental development**. If A uses B, B has to work before A can be tested. So the uses graph tells you what to build first, and which parts of the system can be delivered on their own.
- **Constraints:** what about loops? The notation allows loops in a uses graph, but they are a warning sign. If A uses B and B uses A, neither can be built or tested without the other. They become one big piece of work. Architects try to keep the uses graph loop-free.

"Uses" is stronger than "calls": A can call B without *using* it (e.g. it fires off a notification and doesn't care if it arrives), and A can use B without calling it directly.

<Callout tone="orange" label="Decomposition is not uses">
The same modules appear in both views, but the lines mean different things. In decomposition, a line means *is part of* (and must form a tree). In uses, an arrow means *depends on for correctness* (and can go between any two modules). The lecture's second uses example, an online store, has modules `estore.webapp`, `web::estore`, `web::shared`, `web::accessControl`, `estore.core`, `admin.client`, `admin.core`, `util` and `dao`, joined by «use» arrows. Many of those arrows end at `util` and `dao`, so they have to work before most of the others can be tested.
</Callout>

<Callout tone="orange" label="Common mistake">
Drawing "uses" in a decomposition view, which gives a module two parents. Decomposition is a tree of is-part-of; dependencies go in the uses view. Also, "uses" is not "calls": A uses B only if A's correctness depends on B.
</Callout>
