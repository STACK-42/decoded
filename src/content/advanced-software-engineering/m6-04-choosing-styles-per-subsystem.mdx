# Streamify, Stage 4: Choosing a Style for Each Subsystem

Stages 1 to 3 produced requirements, subsystems, elements and four [derived constraints](/courses/advanced-software-engineering/elements-and-press-play#derived-constraints-for-stage-4). Stage 4 picks the styles. The lecture's key message: **there is no single style for the whole system.**

- The wrong question: *"Which style does Spotify use?"*
- The better question: *"Which style fits each subsystem, given its dominant quality attributes?"*

## The method

For each subsystem:

| Step | Action | Input from |
| --- | --- | --- |
| 1 | Identify its dominant quality attributes | the Stage 1 and Stage 2 tables |
| 2 | List candidate styles | the style catalog ([Lecture 5](/courses/advanced-software-engineering/ten-styles-at-a-glance)) |
| 3 | Evaluate the candidates against the ASRs | QA1, QA3, QA5, QA6, C1 |
| 4 | Choose, and record the reasons, trade-offs and rejected alternatives | an [ADR](/courses/advanced-software-engineering/integrated-architecture-and-evaluation#architecture-decision-records) |

Large systems are heterogeneous: styles are applied locally, then combined.

S7 appears twice: same subsystem, same requirement (QA1), different style in different years.

## Style 1: Client-server

[Client-server](/courses/advanced-software-engineering/n-tier-client-server-and-peer-to-peer#client-server): servers provide services; clients send requests and wait for responses. Clients know the servers; servers don't know the clients in advance.

**Where in Streamify:** every interactive feature: login, search, catalog browsing, playlists, ad decisions, key issuance, and (today) audio delivery from CDN edge servers.

| Requirement | How client-server satisfies it |
| --- | --- |
| C1 licensing | rights checks happen in one trusted, central place; clients can't be trusted |
| QA7 security | tokens, key issuance and payment are centrally controlled and auditable |
| FR4 playlists | one authoritative copy avoids conflicts between devices |
| QA3 scalability | stateless servers behind load balancers scale horizontally |
| C2 many platforms | one API contract; a BFF gateway adapts responses per device |

| Weakness | Mitigation |
| --- | --- |
| the server is a bottleneck / single point of failure | replication, multiple regions, caching, circuit breakers (stop calling a failing service for a while, so the failure doesn't spread) |
| round-trip latency | edge points of presence (server sites close to users), gateway aggregation, client caching |
| bandwidth cost for heavy content | move audio to a CDN, a specialised client-server |

**Rejected: P2P for metadata and playlists.** Authority and consistency can't be enforced on untrusted peers, so licensing (C1) fails.

*Think about it:* a CDN edge is a server too. Why is CDN delivery a specialised form of client-server rather than a separate style? (Because the roles don't change: clients still request, servers still answer. The CDN only moves the servers closer and caches their content.)

## Style 2: Layered

A [layered](/courses/advanced-software-engineering/ten-styles-at-a-glance#layered-architecture) design groups components into layers. Each layer offers services to the layer above and uses only the layer below (**strict**) or any layer below (**relaxed**).

| Requirement | How layering satisfies it |
| --- | --- |
| C2 many platforms | one shared core reused; only the top and bottom layers change per platform |
| QA6 modifiability | a UI redesign doesn't touch the playback engine; a codec change doesn't touch the UI |
| QA7 security | DRM and key handling sit in a protected core layer the UI can't bypass |
| Testability | each layer can be tested with the layer below replaced by a mock |

| Weakness | Mitigation / note |
| --- | --- |
| performance overhead from passing through layers | relaxed layering on the audio data path: the playback engine writes straight to the platform's audio output |
| the <Term id="sinkhole-anti-pattern">"sinkhole" anti-pattern</Term>: requests pass through layers that do nothing with them | watch for it in simple CRUD services (ones that only create, read, update and delete records) |
| doesn't address distribution: it structures one deployable unit | that's why it is combined with client-server |

**Two kinds of view.** Layered answers a [module-view](/courses/advanced-software-engineering/module-views) question: *how is the code organised?* Client-server, P2P and messaging answer a [C&C-view](/courses/advanced-software-engineering/component-and-connector-views) question: *how do running parts interact?* So "should we use layered or client-server?" is the wrong question: they answer different questions, and are combined, not compared.

## Style 3: Peer-to-peer (historic, 2008 to 2014)

[Peer-to-peer](/courses/advanced-software-engineering/n-tier-client-server-and-peer-to-peer#peer-to-peer): every node is both client and server. Peers find each other and exchange resources directly, without a central server in every transfer.

**Context, constraint C5:** in 2008 Spotify was a start-up promising instant play across a huge catalog, and bandwidth was expensive. The ≈ 2.4 Tbps estimate shows why bandwidth dominated the cost. The original desktop client fetched audio chunks from other listeners' clients *and* from Spotify's servers.

**How the hybrid worked** (simplified from Kreitz and Niemelä, IEEE P2P 2010):

1. The first chunk came from a server, for a fast start (protects QA1).
2. In parallel, the client asked the tracker and its neighbours which peers held the track.
3. Later chunks came from peers. The server was the fallback if peers were slow (protects QA2).
4. Audio was encrypted. Peers relayed bytes they couldn't play (C1, QA7).
5. Reported results: most plays from the local cache, a large share from peers, only about 1/10 from servers; median latency about ¼ second.

| Driver | Why P2P fit |
| --- | --- |
| QA8 / C5 cost | users' upload bandwidth carried much of the delivery load |
| QA3 scalability | capacity grows with users: more listeners, more sources (self-scaling) |
| Popularity skew | popular tracks are cached by many peers, so they are copied naturally |

It was **hybrid, not pure P2P**. Pure P2P can't enforce licensing, authentication or royalties.

### Why P2P was retired (~2014)

| What changed | Effect on the architecture |
| --- | --- |
| mobile became dominant | phones make poor peers (battery, data caps, home routers (NAT) that block incoming connections, limits on background apps); they never took part in P2P anyway |
| CDN and server bandwidth costs dropped | the cost driver C5 got weaker, so the main reason for P2P weakened |
| the company grew | it could afford its own and third-party delivery infrastructure |
| complexity and operational risk | P2P is harder to debug and monitor, and using users' resources worried users |
| need for more predictable quality | a CDN gives controllable latency and is simpler to reason about for availability |

**Key lesson:** the same requirement (QA1, instant play) was met by different styles at different times, because the constraints and context changed. It was recorded as ADR-001 (hybrid P2P, 2008), <Term id="superseded">superseded</Term> by ADR-004 (CDN delivery, ~2014).

## Style 4: Pipe-and-filter

[Pipe-and-filter](/courses/advanced-software-engineering/pipe-and-filter-and-messaging#pipe-and-filter): independent filters transform data and pass the results through pipes to the next filter. Filters don't share state and don't know their neighbours.

The same pattern runs S12's royalty batch: events in → de-duplicate → aggregate per rights holder → reports.

| Requirement | How pipe-and-filter satisfies it |
| --- | --- |
| throughput (terabytes of content and events) | filters run in parallel and scale independently (add transcoders only) |
| QA6 extensibility | a new codec or ML feature = insert a filter; the other stages don't change |
| Reuse | "dedupe" and "rights filter" are reused across pipelines |
| Testability | each filter is a near-pure transformation, tested on its own |
| Recoverability | durable pipes: a failed stage re-runs from its input |

| Weakness | Mitigation |
| --- | --- |
| latency adds up across stages | never use it for "press play" (interactive) |
| coupling through the data format | schemas (formats such as Avro or Protobuf) with versioning |
| errors spread across stages | <Term id="dead-letter-queue">dead-letter queues</Term> and idempotent filters |
| serialisation overhead | accepted for batch and bulk work |

**Rejected: one monolithic "ingest service".** A new codec would mean redeploying everything, and a slow transcoder would block validation.

## Style 5: Messaging (publish/subscribe)

[Messaging](/courses/advanced-software-engineering/ten-styles-at-a-glance#implicit-invocation-and-its-two-flavors): components communicate by sending messages through a broker. Producers don't know consumers. They are decoupled in **time** (asynchronous), **space** (no addresses) and **synchronisation** (no blocking).

Real-world anchor: Spotify's engineering blog (2016) described moving its event delivery from Kafka to Google Cloud Pub/Sub, for reliable delivery of royalty-relevant events.

| Requirement | How messaging satisfies it |
| --- | --- |
| ~700 K events/s peak | the broker absorbs bursts (buffering, load levelling); consumers work at their own pace |
| QA5 no lost royalty events | durable topics, <Term id="at-least-once">at-least-once delivery</Term>, client-side retry buffers, <Term id="idempotent">idempotent</Term> consumers that de-duplicate by event ID |
| QA1 latency | clients fire and forget; telemetry never blocks playback (derived constraint 1) |
| QA6 modifiability | a new consumer (e.g. a new analytics team) subscribes without changing producers |
| QA4 availability | if royalty processing goes down, events wait in the bus; producers are unaffected |
| Reprocessing | retention and replay allow recomputing after a bug fix in a consumer |

Three of the four quality ASRs (QA1, QA5, QA6) are served by this one style. That's why S9 is architecturally significant even though users never see it. **"At-least-once + dedupe = effectively once":** the bus guarantees nothing is lost; the consumer (the royalty aggregator) removes duplicates.

| Weakness | Mitigation in Streamify |
| --- | --- |
| eventual consistency: consumers lag behind | acceptable for analytics and royalties (daily); not used where read-your-writes matters |
| duplicate delivery (at-least-once) | unique event IDs and idempotent processing / a dedupe filter |
| ordering only within a partition | partition by user ID or track ID where order matters |
| harder to trace end to end | correlation IDs, distributed tracing, schema registry |
| the broker is critical infrastructure | managed, replicated broker across zones |

**Rejected: clients calling a synchronous `POST /royalty/play`.** That creates <Term id="temporal-coupling">temporal coupling</Term>: if the royalty service is down, events are lost or playback slows down, breaking QA1 and QA5.

*Think about it:* pipe-and-filter and messaging both use queues. What separates them? (A pipe carries a stream to *the next transformation step* in a fixed chain. A topic carries a *fact* to any number of independent subscribers, which the producer doesn't know about.)

<Callout tone="orange" label="Common mistake">
Asking "which style does this system use?" and picking one. Streamify uses five, each where its strengths match a subsystem's dominant qualities. Another trap is comparing layered with client-server: one organises code, the other organises running parts, so you use both.
</Callout>
