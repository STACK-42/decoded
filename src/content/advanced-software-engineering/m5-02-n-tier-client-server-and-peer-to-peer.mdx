# N-Tier, Client-Server and Peer-to-Peer

Three styles that differ in one big question: **who serves whom?** In client-server, one side always asks and the other always answers. In peer-to-peer, everyone does both.

## The n-tier client-server pattern

The <Term id="n-tier">n-tier</Term> style is a layered architecture: the system is split into **tiers**, each with one job.

The browser here is a <Term id="thin-client">thin client</Term>: almost all the work happens on the servers.

## Client-server

Operating Systems covers the mechanisms underneath, sockets, RPC and pipes, in [communication in client-server systems](/courses/operating-systems/interprocess-communication#communication-in-client-server-systems). Here we look at client-server as an architectural style.

In <Term id="client-server">client-server</Term>, client processes interact with individual server processes, usually on a separate computer, to access data or a resource. **A server may in turn use the services of other servers**, so the same process can be a server to one side and a client to the other.

**Examples** (from the lecture's styles summary): browsers such as Chrome request pages from web servers such as Apache or Nginx over HTTP; email clients talk to mail servers over SMTP/IMAP.

### Key properties

- **<Term id="separation-of-concerns">Separation of concerns</Term>:** each tier handles one concern (display, business rules, data).
- **<Term id="synchronous-communication">Synchronous communication</Term>:** requests flow in a single direction, from the client tier through the web and business-logic tiers to the data tier, and each caller waits for the answer.
- **Flexible deployment** (which tier runs where is a [deployment view](/courses/advanced-software-engineering/allocation-views#the-deployment-style) question from Lecture 4): there are no restrictions on how a multi-tier application is deployed. All tiers can run on one machine, or, at the other extreme, each tier on its own machine.

### Addressing quality attributes

| Quality | How n-tier client-server handles it |
| --- | --- |
| **Availability** | Servers in each tier can be <Term id="replication">replicated</Term>, so one failure doesn't stop the tier. |
| **Modifiability** | Separation of concerns: change the UI without touching the data tier. |
| **Performance** | Depends on the speed of the connections between tiers, and on how much data is transferred across them. Every tier boundary adds a network hop. |
| **Scalability** | Does the tier type matter? Yes: stateless tiers (web, application) scale by adding servers; the data tier is the hard one, because copies of data must stay consistent. |

### Pros and cons (from the styles summary)

| Pros | Cons |
| --- | --- |
| centralized data and control | the server is a single point of failure |
| easier security and backups | the server can become a bottleneck |
| thin clients, easy updates | depends on the network |

<Callout tone="orange" label="The weak spot">
A single server is a <Term id="single-point-of-failure">single point of failure</Term> and can become a bottleneck. That's why replication is the first availability tactic in this style.
</Callout>

## Peer-to-peer

In <Term id="peer-to-peer">peer-to-peer</Term> (P2P), **all processes play similar roles**, cooperating as peers to perform distributed activities or computations, with no distinction between clients and servers. Each peer is both: it asks for resources and serves them.

**Examples:** BitTorrent (every downloader also uploads pieces to others) and Bitcoin (nodes share transactions and blocks without a central server).

**A hybrid: P2P with a centralized index server**, as in the original Napster. Peers transfer files directly to each other, but a central server keeps the index of who has what. Searching is easy, but the index server is a single point of failure again.

### Pros and cons

| Pros | Cons |
| --- | --- |
| highly scalable: every new peer adds capacity | hard to secure: you must trust unknown peers |
| no single point of failure | hard to manage and back up |
| resources spread across the peers | performance and availability vary with which peers are online |

<Callout tone="orange" label="Common mistake">
Thinking n tiers need n machines. A tier is a logical layer; the lecture says all tiers can run on one machine or each on its own. Tier count is a design choice; machine count is a deployment choice.
</Callout>
