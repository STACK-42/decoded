# Views and Structures

A real system is too rich to show in one picture. Lecture 4 is about how architects describe it with several pictures instead, each called a **view**.

## One architecture, many views

The lecture opens with an equation drawn as books:

> **Documentation of an architecture = the relevant views + documentation that applies beyond any one view.**

Which views are "relevant"? It depends on what you and the other stakeholders care about most:

- **different views expose different <Term id="quality-attribute">quality attributes</Term> to different degrees.** A deployment view (which software runs on which machine) tells you a lot about performance and availability, and almost nothing about how easy the code is to change;
- **different views support different goals,** and highlight different elements and relations.

**Can a single view represent an architecture?** No. Recall the definition from [Lecture 2](/courses/advanced-software-engineering/complexity-architecture-and-design#what-is-software-architecture): architecture is the *set of structures* needed to reason about the system. "Set" is plural on purpose.

## Structures versus views

- A **<Term id="structure">structure</Term>** is the set of elements itself, as it exists in the system (the code, the running processes, the hardware).
- A **<Term id="view">view</Term>** is a *representation* of a coherent set of architectural elements: it shows a set of elements and the relations among them.

So **a view is a representation of one or more structures.** A structure is the territory; a view is a map of it.

<Callout tone="orange" label="Same word, different meaning">
Lecture 2 used "structure" for one of software's two values: [structure vs behavior](/courses/advanced-software-engineering/the-economics-of-architecture#two-values-behavior-and-structure), meaning how easy the system is to change. Here a structure is a concrete set of elements in the system (the modules, or the running processes). Both are about architecture, but they answer different questions.
</Callout>

The lecture illustrates "one system, many views" with the cover of *Gödel, Escher, Bach*: one carved block casts the shadow "G" from one side, "E" from another and "B" from a third. Each shadow holds *some* of the information; only the block holds *all* of it.

## Three kinds of structures

Architectural structures fall into three groups, matching three broad kinds of decisions an architect makes:

| Kind | Elements | The question it answers |
| --- | --- | --- |
| **Module structures** | units of implementation (packages, classes, files) | How is the code divided up, and who uses what? |
| **Component-and-connector (C&C) structures** | runtime units (processes, servers, data stores) and their interactions | How does the system behave while it runs? |
| **Allocation structures** | software elements mapped to non-software things (hardware, files, teams) | Where does the software run, live and get built? |

The next three lessons take one kind each: [module views](/courses/advanced-software-engineering/module-views), [C&C views](/courses/advanced-software-engineering/component-and-connector-views) and [allocation views](/courses/advanced-software-engineering/allocation-views).

## Module versus component

This distinction trips people up, so the lecture asks a series of questions:

- **Static or dynamic?** A <Term id="module">module</Term> is static: it exists in the code. A <Term id="component">component</Term> is dynamic: it exists while the system runs.
- **Unit of implementation or runtime entity?** Module = unit of implementation. Component = runtime entity.
- **Where do source code, XML files, config files and parser grammar files fit?** They are implementation artifacts, so they belong to the module world.
- **An executable binary?** It sits in between: it is produced from modules, and when it runs it becomes one or more components. Allocation views (the install style) describe exactly this mapping.
- **"Every module becomes exactly one component at runtime, so who cares?"** **No.** The mapping isn't one-to-one:
  - **one module can become many components.** One `Server` module can run as many server processes at once;
  - **many modules can become one component.** A dozen packages compile into a single running client.

<Callout tone="violet" label="Who cares?">
You do, as soon as you ask about performance or availability. Those depend on how many components run and where, which the module view doesn't show. Modifiability depends on how the code is divided, which the C&C view doesn't show. That's why you need both.
</Callout>

<Callout tone="orange" label="Common mistake">
Treating one diagram as "the architecture," or treating module and component as synonyms. A module is code you build; a component is something that runs. One Client module can run as ten client components.
</Callout>
