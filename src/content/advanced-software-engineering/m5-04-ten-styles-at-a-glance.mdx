# Ten Architecture Styles at a Glance

Lecture 5 comes with a one-page summary of all ten styles: a short definition, a real-life example, and the key pro and con of each. This lesson puts them side by side, then covers the five not yet explained in detail: implicit invocation, publish-subscribe, event-based, <Term id="web-services">web services</Term> and <Term id="microservices">microservices</Term>.

## The summary table

| # | Style | In one line | Real-life example | Key pro | Key con |
| --- | --- | --- | --- | --- | --- |
| 1 | **Layered (n-tier)** | stacked layers; each uses only the one below | Android OS stack | separation of concerns | overhead and rigid layers |
| 2 | **Client-server** | clients request; a central server responds | the Web, email | central control and security | single point of failure |
| 3 | **Peer-to-peer** | equal peers share resources directly | BitTorrent, Bitcoin | scalable, no central failure point | hard to secure and manage |
| 4 | **Pipe-and-filter** | data flows through chained transform steps | Unix pipes, GCC | reusable, composable filters | poor for interactive apps |
| 5 | **Messaging** | async messages through broker queues | LinkedIn Kafka, order queues | loose coupling, reliable delivery | broker complexity, hard debugging |
| 6 | **Implicit invocation** | announced events trigger registered procedures | browser DOM events, DB triggers | easy to extend | unpredictable execution order |
| 7 | **Publish-subscribe** | publishers post to topics; subscribers receive | Spotify on Cloud Pub/Sub | scales to many consumers | hard to trace message flow |
| 8 | **Event-based** | plug-ins react to platform events | Eclipse IDE, VS Code | highly extensible | complex control flow |
| 9 | **Web services** | services exposed over HTTP (SOAP / REST) | Google Maps API, Expedia | interoperable, platform-independent | network latency and payload overhead |
| 10 | **Microservices** | small independent services, each owning its data | Netflix | independent deploy and scaling | distributed-system complexity |

## Layered architecture

The system is organized into horizontal layers (e.g. presentation, business, data). **Each layer only uses the services of the layer directly below it.** The Android platform is layered: apps → Java API framework → native libraries and Android Runtime → hardware abstraction layer → Linux kernel. The TCP/IP network stack follows the same idea.

- **Pros:** clear separation of concerns; easy to test and maintain per layer; layers are replaceable and reusable.
- **Cons:** performance overhead crossing layers; changes may ripple through all layers; can become monolithic.

N-tier client-server, from [the previous lesson](/courses/advanced-software-engineering/n-tier-client-server-and-peer-to-peer), is the layered style spread over machines.

**<Term id="implicit-invocation">Implicit invocation</Term>.** Instead of calling procedures directly, a component announces an event; other components register interest and are invoked automatically when it occurs. *Examples:* JavaScript handlers added with `addEventListener("click", …)` run when you click; database triggers run when a row is inserted or updated.

- **Pros:** strong decoupling; easy to add components; supports reuse and evolution.
- **Cons:** no control over the order handlers run in; hard to reason about correctness; hard to debug.

**<Term id="publish-subscribe">Publish-subscribe</Term>** (lecture example: Spotify). Publishers send messages to **topics** without knowing who receives them; subscribers receive every message on the topics they follow. Spotify moved this pipeline to Google Cloud Pub/Sub in 2016.

- **Pros:** publishers and subscribers fully decoupled; scales to many consumers; subscribers can be added at any time.
- **Cons:** delivery and ordering guarantees vary; hard to trace the message flow; managing topics and schemas is overhead.

**<Term id="event-based">Event-based</Term>** (lecture example: the Eclipse IDE). Components produce and react to events. Eclipse plug-ins register listeners and extension points and react to editor, workspace and UI events. VS Code is similar: it loads extensions on "activation events."

- **Pros:** highly extensible (plug-ins); responsive behavior; components developed independently.
- **Cons:** complex, non-linear control flow; testing event chains is hard; risk of event storms and leaks.

<Callout tone="orange" label="Messaging vs publish-subscribe">
Both use a broker. In [messaging](/courses/advanced-software-engineering/pipe-and-filter-and-messaging#messaging), each message in a queue is removed by *one* receiver. In publish-subscribe, *every* subscriber to a topic gets its own copy.
</Callout>

## Web services

Functionality is exposed as services over standard web protocols: HTTP with SOAP/WSDL (XML messages, described by a WSDL file), or REST/JSON (plain HTTP requests carrying JSON). Programs on any platform, in any language, can call them. *Examples:* Expedia and Skyscanner pull flight and hotel data from airline and hotel services; Uber and many others call the Google Maps API.

- **Pros:** platform- and language-independent; standard, interoperable protocols; services reused across apps.
- **Cons:** network latency; payload overhead (XML/JSON); versioning and security challenges.

## Microservices

The application is a set of small, independently deployable services. **Each owns its data and one business capability** (the [Single Responsibility Principle](/courses/advanced-software-engineering/design-principles-and-srp#responsibility--actor) at service scale: one service, one reason to change), and they talk through APIs or messaging. *Example:* after a major database outage in 2008, Netflix split its monolith into hundreds of microservices on AWS (streaming, billing, recommendations), each deployed and scaled on its own. Amazon and Uber work the same way.

Clients reach the services through an <Term id="api-gateway">API gateway</Term>, which routes each request to the right service.

- **Pros:** independent deployment and scaling; technology freedom per service; fault isolation.
- **Cons:** distributed-system complexity; keeping data consistent across services is hard (often only <Term id="eventual-consistency">eventual consistency</Term>); high DevOps and monitoring effort.

<Callout tone="orange" label="Remember the First Law">
Lecture 2 used microservices as its example of the [First Law](/courses/advanced-software-engineering/the-architects-role#the-laws-of-software-architecture): independent scaling, paid for with network latency, distributed transaction failures and deployment complexity. And the [2002 data center case](/courses/advanced-software-engineering/the-architects-role#two-case-studies-architecture-depends-on-context) explains why this style only became common once containers made services cheap.
</Callout>

<Callout tone="orange" label="Common mistake">
Mixing up messaging and publish-subscribe. In a queue, each message is taken by one receiver; in pub/sub, every subscriber gets a copy. And drawing "microservices" that share one database: that couples them, so they can't change or deploy independently.
</Callout>
