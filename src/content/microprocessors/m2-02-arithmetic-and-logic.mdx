# Arithmetic and Logic Instructions

Every program eventually comes down to doing math or manipulating bits: adding totals, calculating memory offsets, or isolating status bits. These operations route data directly through the processor's internal [ALU](/courses/computer-organization/inside-the-cpu). Most two-operand instructions overwrite the first operand with the calculation result: `ADD AX, BX` computes the sum $AX + BX$ and stores it in `AX`.

## Add and subtract

The 8086 provides a complete set of instructions for basic addition and subtraction:

| Instruction | Effect | Description |
|---|---|---|
| `ADD a, b` | $a = a + b$ | Add source to destination |
| `ADC a, b` | $a = a + b + \text{CF}$ | Add with carry flag |
| `SUB a, b` | $a = a - b$ | Subtract source from destination |
| `SBB a, b` | $a = a - b - \text{CF}$ | Subtract with borrow (carry flag) |
| `INC a` | $a = a + 1$ | Increment by 1 |
| `DEC a` | $a = a - 1$ | Decrement by 1 |
| `NEG a` | $a = -a$ | Negate using two's complement |
| `CMP a, b` | Flags set from $a - b$ | Compare operands, discard result |

To change the algebraic sign of a signed number, the processor performs **two's complement negation** via the `NEG` instruction. The CPU computes the two's complement by inverting every bit of the operand (bitwise NOT) and then adding 1 to the result, effectively turning positive numbers into negative numbers and vice versa.

Watch the [flags](/courses/microprocessors/flags) as you step through this sequence:

<AsmRunner source={`MOV AL, 250
ADD AL, 10      ; 260 doesn't fit in 8 bits: CF = 1
MOV AH, 0
ADC AH, 0       ; pick up the carry, so AX = 260
MOV BX, 5
SUB BX, 5       ; zero: ZF = 1
DEC BX          ; 0 - 1 wraps to FFFFh: SF = 1
NEG BX          ; back to 1`} />

Because an 8086 register holds at most 16 bits, adding numbers wider than 16 bits (such as 32-bit or 64-bit integers) requires **multi-precision addition**. The program breaks each large number into 16-bit chunks, adds the lowest chunks first using standard `ADD`, and then uses **carry propagation** with `ADC` (Add with Carry) to pass any overflow bit into the addition of the higher chunks.

For example, consider adding two 32-bit numbers: `0002_9000h` and `0001_8000h`.

1. Low 16 bits: The CPU executes `ADD AX, 8000h` where `AX = 9000h`. The sum is `9000h + 8000h = 11000h`. Register `AX` receives the lower 16 bits (`1000h`), and the carry flag is set (`CF = 1`) because the sum exceeded 16 bits.
2. High 16 bits: The CPU executes `ADC DX, 0001h` where `DX = 0002h`. Because `CF = 1`, the calculation performed is `DX = 0002h + 0001h + 1 = 0004h`.
3. The combined 32-bit result in `DX:AX` is `0004_1000h`, which matches the mathematical sum $00029000h + 00018000h = 00041000h$.

<Callout tone="orange" label="Trap: INC and DEC do not update the carry flag">
The increment (`INC`) and decrement (`DEC`) instructions update the zero (ZF), sign (SF), overflow (OF), parity (PF), and auxiliary carry (AF) flags, but they leave the carry flag (CF) completely unchanged. This hardware design allows you to use `INC` or `DEC` to update loop counter pointers in memory during a multi-precision addition loop without destroying the carry bit generated by `ADD` or `ADC`. However, if you rely on `INC` to detect unsigned wrapping from `0FFh` back to `00h`, CF will remain 0; use `ADD reg, 1` if you need the carry flag updated.
</Callout>

## Multiply and divide

Unlike addition and subtraction where you specify both destination and source registers, multiplication and division use **implicit operands**: registers that are not written in the assembly code line, but are permanently hardwired into the instruction logic by the CPU architecture.

Because multiplying two $n$-bit numbers can generate a result up to $2n$ bits wide, the destination register must be twice as large as the multiplier. Similarly, division accepts a $2n$-bit dividend and divides it by an $n$-bit divisor, producing both a quotient and a remainder.

| Instruction | Operand size | Operands involved | Result storage |
|---|---|---|---|
| `MUL BL` | 8-bit unsigned | `AL` $\times$ `BL` | `AX` receives 16-bit product |
| `MUL BX` | 16-bit unsigned | `AX` $\times$ `BX` | `DX:AX` receives 32-bit product (`DX` high, `AX` low) |
| `DIV BL` | 8-bit unsigned | `AX` $\div$ `BL` | `AL` = quotient, `AH` = remainder |
| `DIV BX` | 16-bit unsigned | `DX:AX` $\div$ `BX` | `AX` = quotient, `DX` = remainder |

The notation `DX:AX` means the two 16-bit registers act together as a single 32-bit number, with `DX` holding the most significant 16 bits and `AX` holding the least significant 16 bits.

The unsigned instructions are `MUL` and `DIV`. For signed arithmetic, the 8086 provides `IMUL` and `IDIV`. Before performing a signed division, a smaller dividend must be widened to twice its size using **sign extension**, which duplicates the most significant sign bit across the new upper register. The instruction `CBW` (Convert Byte to Word) sign-extends `AL` into `AX`, and `CWD` (Convert Word to Doubleword) sign-extends `AX` into `DX:AX`.

<AsmRunner source={`MOV AL, 20
MOV BL, 30
MUL BL          ; AX = 600
MOV AX, 17
MOV BL, 5
DIV BL          ; AL = 3, AH = 2`} />

When performing division, the quotient must fit into the assigned destination register (`AL` for an 8-bit divisor, or `AX` for a 16-bit divisor). If the quotient is too large to fit in that register, or if the divisor is zero, the CPU experiences a divide overflow error. When this occurs, the hardware immediately halts execution of the instruction and triggers Interrupt 0 (divide error exception).

<Callout tone="orange" label="Trap: divide error when quotient exceeds destination">
Dividing by zero is not the only way to crash a division instruction. Consider `MOV AX, 1000h` (4,096 decimal) followed by `MOV BL, 2` and `DIV BL`. Mathematically, $4096 \div 2 = 2048$. However, `DIV BL` stores the quotient in the 8-bit register `AL`, which can hold unsigned values only up to 255. Because 2,048 exceeds 255, the CPU cannot store the quotient and generates a hardware divide error interrupt (INT 0), crashing the program. Whenever dividing large numbers by small divisors, ensure you use 16-bit division (`DIV BX`).
</Callout>

## Logic: working on individual bits

Every bit in a byte or word can represent an independent flag or setting. The technique of isolating, changing, or checking specific bit positions while keeping all other bits unchanged is known as **bit masking**. In a bit mask, zeros and ones act as digital filters when combined with boolean logic operations:

- **Clearing bits with `AND`**: Any bit ANDed with 0 becomes 0, while any bit ANDed with 1 keeps its original value. To clear the top nibble of `AL` and preserve the low nibble, use `AND AL, 0Fh` (`0Fh = 0000 1111b`).
- **Setting bits with `OR`**: Any bit ORed with 1 becomes 1, while any bit ORed with 0 remains unchanged. To turn on bit 7 (the high bit), use `OR AL, 80h` (`80h = 1000 0000b`).
- **Toggling bits with `XOR`**: Any bit XORed with 1 inverts its state (0 becomes 1, 1 becomes 0), while any bit XORed with 0 remains unchanged. `XOR AL, 20h` toggles bit 5. Additionally, XORing any register with itself (`XOR AX, AX`) is the standard assembly idiom to clear a register to 0 in fewer instruction bytes than `MOV AX, 0`.
- **Inverting all bits with `NOT`**: Produces the one's complement by flipping every 0 to 1 and every 1 to 0.
- **Checking bits with `TEST`**: Performs an internal logical AND between operands, updating the status flags (such as the zero flag, ZF) without modifying either operand. `TEST AL, 01h` sets `ZF = 1` if bit 0 is zero (even number) and `ZF = 0` if bit 0 is one (odd number).

| Instruction | Common operation | Flags affected | Primary masking purpose |
|---|---|---|---|
| `AND dest, mask` | Clear bits | Sets ZF, SF, PF; clears CF, OF | Isolate fields by zeroing unneeded bits |
| `OR dest, mask` | Set bits | Sets ZF, SF, PF; clears CF, OF | Force specific control bits to 1 |
| `XOR dest, mask` | Toggle bits | Sets ZF, SF, PF; clears CF, OF | Invert specific bits or clear registers |
| `NOT dest` | One's complement | None | Invert every bit in the operand |
| `TEST dest, mask` | Inspect bits | Sets ZF, SF, PF; clears CF, OF | Test bit values without changing register |

<AsmRunner source={`MOV AL, 'a'       ; 61h = 01100001
AND AL, 11011111b ; clear bit 5: now 'A'
OR  AL, 00100000b ; set bit 5: 'a' again
XOR AL, 00100000b ; flip bit 5: 'A' again
TEST AL, 1        ; odd or even? ZF = 0 means odd`} />

The ASCII character set was intentionally designed so that uppercase and lowercase letters differ by only a single bit (bit 5). Clearing bit 5 with `AND` converts lowercase to uppercase, while setting bit 5 with `OR` converts uppercase to lowercase.

## Shifts and rotates

Microprocessors manipulate bits geometrically by sliding them left or right. The fundamental difference between a **shift** and a **rotate** lies in what happens to the bits that fall off the edge:

- In a **shift**, bits displaced off the end exit the register and fall into the carry flag (CF). Empty bit positions opened up at the opposite end are filled with zeros (in `SHL` and `SHR`) or filled with a duplicate of the sign bit (in `SAR`).
- In a **rotate**, bits shifted off one end loop back around and re-enter the register at the opposite end (`ROL` and `ROR`), ensuring no bits are discarded.

The shift or rotate count is either 1 or stored in register `CL` on the original 8086 processor (`SHL AL, 3` was added in later processors and is accepted by this simulator).

| Instruction | Full name | Direction | Incoming bit | Mathematical effect |
|---|---|---|---|---|
| `SHL dest, count` | Shift Logical Left | Left | 0 enters right | Multiplies unsigned/signed by $2^{\text{count}}$ |
| `SHR dest, count` | Shift Logical Right | Right | 0 enters left | Divides unsigned number by $2^{\text{count}}$ |
| `SAR dest, count` | Shift Arithmetic Right | Right | Sign bit copied | Divides signed number by $2^{\text{count}}$ |
| `ROL dest, count` | Rotate Left | Left | Bit from left enters right | Bitwise circular rotation |
| `ROR dest, count` | Rotate Right | Right | Bit from right enters left | Bitwise circular rotation |

The bit that falls off the edge always lands in the carry flag (CF), allowing you to inspect it with conditional jump instructions.

<AsmRunner source={`MOV AL, 3
SHL AL, 1       ; 6
SHL AL, 1       ; 12
SHR AL, 1       ; 6
MOV BL, 11110000b
SAR BL, 1       ; -16 becomes -8: the sign is kept
ROL BL, 1       ; the top bit comes round`} />

<Callout tone="orange" label="Trap: SHR versus SAR on negative values">
`SHR` (Shift Logical Right) and `SAR` (Shift Arithmetic Right) both move bits to the right, but treat the leftmost sign bit differently. `SHR` always shifts a zero into the most significant bit. If you use `SHR` on a signed negative value such as `-16` (`1111 0000b`), it becomes `0111 1000b` (`+120`), corrupting the sign. In contrast, `SAR` duplicates the existing sign bit (shifting in a 1 for negative numbers and 0 for positive numbers), producing `1111 1000b` (`-8`), accurately dividing the signed integer by 2.
</Callout>

<Callout tone="violet" label="Why shifting matters">
A shift instruction executes in 2 clock cycles on an 8086, whereas the `MUL` instruction takes between 70 and 118 clock cycles. Because of this massive speed difference, optimizing compilers replace multiplications and divisions by constants that are powers of 2 (such as 2, 4, 8, 16) with equivalent bit shifts whenever possible.
</Callout>

## Practice by hand

Work through these arithmetic and bitwise calculation problems to master how the 8086 computes and tracks status flags.

### Problem 1: Multiplication and division trace

Determine the exact register values resulting from each of the following independent instruction sequences:

1. Sequence A:
   ```nasm
   MOV AL, 12h
   MOV BL, 10h
   MUL BL
   ```
   What is the value in `AX` in hexadecimal?

2. Sequence B:
   ```nasm
   MOV AX, 0105h
   MOV BL, 10h
   DIV BL
   ```
   What are the values in `AL` (quotient) and `AH` (remainder) in hexadecimal?

3. Sequence C:
   ```nasm
   MOV AX, 0FFFh
   MOV BL, 02h
   DIV BL
   ```
   Explain what happens when this sequence is executed.

<ModelAnswer>
1. **Sequence A (8-bit MUL)**:
   - `AL = 12h` (decimal 18).
   - `BL = 10h` (decimal 16).
   - `MUL BL` multiplies `AL * BL` and stores the 16-bit product in `AX`.
   - Calculation: $18 \times 16 = 288$ decimal.
   - In hexadecimal: $288 = 1 \times 256 + 2 \times 16 + 0 = \text{0120h}$.
   - Result: `AX = 0120h`.

2. **Sequence B (8-bit DIV)**:
   - `AX = 0105h` (decimal 261).
   - `BL = 10h` (decimal 16).
   - `DIV BL` divides `AX` by `BL`.
   - Integer quotient: $261 \div 16 = 16$ (which is `10h`), stored in `AL`.
   - Remainder: $261 - (16 \times 16) = 5$ (which is `05h`), stored in `AH`.
   - Result: `AL = 10h`, `AH = 05h`.

3. **Sequence C (Divide overflow error)**:
   - `AX = 0FFFh` (decimal 4,095).
   - `BL = 02h` (decimal 2).
   - `DIV BL` attempts to divide $4095 \div 2 = 2047$ with remainder 1.
   - The quotient must be stored in 8-bit register `AL`. However, the maximum unsigned number an 8-bit register can hold is 255 (`0FFh`). Because 2,047 exceeds 255, the quotient overflows `AL`.
   - The CPU aborts the instruction and generates a hardware **Interrupt 0 (divide error exception)**, halting or terminating the program.
</ModelAnswer>

### Problem 2: 32-bit addition with carry propagation

A programmer needs to add two 32-bit integers in 8086 assembly:
- Value 1: `0012_8400h` (high word `0012h` in `CX`, low word `8400h` in `AX`).
- Value 2: `0005_9320h` (high word `0005h` in `DX`, low word `9320h` in `BX`).

The addition is carried out with these two instructions:
```nasm
ADD AX, BX
ADC CX, DX
```

1. Compute the low 16-bit addition (`ADD AX, BX`). State the resulting value in `AX` in hexadecimal and the state of the carry flag (CF).
2. Compute the high 16-bit addition with carry (`ADC CX, DX`). State the resulting value in `CX` in hexadecimal.
3. What is the full 32-bit sum represented by the register pair `CX:AX`?

<ModelAnswer>
1. **Low 16-bit addition (`ADD AX, BX`)**:
   - `AX = 8400h = 1000 0100 0000 0000b`
   - `BX = 9320h = 1001 0011 0010 0000b`
   - Sum:
     ```
         8400h
       + 9320h
       -------
        11720h
     ```
   - Register `AX` holds the lower 16 bits: **`1720h`**.
   - Because the 16-bit addition generated a 17th carry-out bit ($11720h > FFFFh$), the carry flag is set: **`CF = 1`**.

2. **High 16-bit addition with carry (`ADC CX, DX`)**:
   - `CX = 0012h`
   - `DX = 0005h`
   - Carry flag from previous step: `CF = 1`.
   - The formula for `ADC` is $CX + DX + \text{CF}$:
     ```
         0012h
       + 0005h
       + 0001h (from CF)
       -------
         0018h
     ```
   - Register `CX` receives: **`0018h`**.
   - No carry out was generated from this word, so `CF = 0`.

3. **Combined 32-bit sum (`CX:AX`)**:
   - High word (`CX`): `0018h`
   - Low word (`AX`): `1720h`
   - Final 32-bit result: **`0018_1720h`**.
   - Verification in decimal: $00128400h + 00059320h = 1213440 + 365344 = 1578784 = 00181720h$.
</ModelAnswer>
