# Input and Output

A central processing unit executes billions of instructions per second, completing an operation every fraction of a nanosecond. Peripherals operate on completely different physical scales: a mechanical keyboard delivers a few keystrokes per second, a magnetic hard disk takes milliseconds to seek a track, and a network controller receives packets at microsecond intervals. Connecting devices directly to the high-speed CPU datapath would freeze the entire processor. Input and output systems exist to bridge this vast chasm in speed, data format, and electrical characteristics.

## Devices and the I/O Controller

A peripheral never connects directly to the CPU registers or the high-speed system bus. Doing so would force the processor to understand the mechanical, optical, and analog electrical quirks of every peripheral manufacturer. Instead, each peripheral interfaces through an **I/O module**, also called a **device controller**.

```
+--------------------------------------------------------------+
|                         System Bus                           |
+------------------------------+-------------------------------+
                               |
                   +-----------v-----------+
                   |     I/O Controller    |
                   |                       |
                   |  [ Data Register ]    |
                   |  [ Status Register ]  |
                   |  [ Command Register ] |
                   +-----------+-----------+
                               | Device-Specific Interface
                   +-----------v-----------+
                   |   Peripheral Device   |
                   +-----------------------+
```

An I/O controller performs three main functions:

1. **Electrical isolation and adaptation**: It converts system bus signal voltages and timings into whatever signaling standard the external cable requires (such as USB, SATA, PCIe, or Ethernet).
2. **Buffering**: It contains internal semiconductor memory called a **buffer**. A disk drive reads an entire 4,096-byte sector in a single mechanical sweep. The controller buffer holds these bytes until the system bus is ready to receive them, matching the burst speed of the disk to the available bandwidth of the system.
3. **Data formatting**: It translates between the parallel data words used across the motherboard and the serial bit streams sent over modern external cables.

### Controller Register Architecture

To control a peripheral, the processor communicates with a set of dedicated registers built into the controller:

- **Data In / Data Out Registers**: Hold the byte or word currently moving to or from the peripheral.
- **Status Register**: A bitmask read by the CPU to monitor device state:
  - `BUSY`: Set to 1 while the peripheral is executing an internal operation.
  - `READY` or `DONE`: Set to 1 when input data is waiting in the data register, or when the output buffer is empty and ready to accept the next byte.
  - `ERROR`: Set to 1 if parity checks, cyclic redundancy checks (CRC), or timeouts fail.
  - `IRQ`: Asserted when the controller needs the CPU's attention.
- **Command / Control Register**: Accepts operational codes written by the CPU, specifying read, write, seek, media format, or interrupt-enable configurations.

## I/O Addressing: Memory-Mapped vs. Port-Mapped

How does the processor address these controller registers? Computer architectures use two primary models:

| Architectural Property | Memory-Mapped I/O (MMIO) | Port-Mapped I/O (PMIO / Isolated I/O) |
|---|---|---|
| **Address Space** | Shares physical DRAM address space | Dedicated, separate I/O address space |
| **CPU Instructions** | Standard `LDR`, `STR`, `MOV` instructions | Specialized `IN`, `OUT` machine instructions |
| **Bus Control Signals** | Unified $\overline{\text{MEMR}}$ and $\overline{\text{MEMW}}$ lines | Separate $\overline{\text{IOR}}$ and $\overline{\text{IOW}}$ bus lines |
| **Virtual Memory Protection** | Standard page table permissions apply | Requires separate CPU privilege check |
| **Caching Considerations** | Pages must be marked uncacheable | Naturally immune to cache pollution |
| **Architectures** | ARM, RISC-V, MIPS, modern x86 PCIe | Legacy x86 (Intel 8086 through Core i9) |

Under **Memory-Mapped I/O** (**MMIO**), device registers occupy regular physical memory addresses. When the CPU executes a store instruction to address `0xFFFF0000`, the address decoder on the bus activates the chip-select line of the I/O controller rather than system DRAM. This allows all addressing modes, index registers, and arithmetic operations to interact with peripheral registers directly. However, these address regions must be marked uncacheable in the [page table](/courses/computer-architecture/virtual-memory#the-page-table-and-page-table-entries-pte), or the CPU cache would intercept writes and return stale register readings.

Under **Port-Mapped I/O** (**PMIO**), also called **isolated I/O**, I/O ports reside in a completely separate address space. The CPU provides dedicated hardware instructions, such as `IN AL, DX` and `OUT DX, AL` on x86 processors, which assert distinct bus control lines ($\overline{\text{IOR}}$ and $\overline{\text{IOW}}$) to distinguish I/O access from DRAM access.

<Callout tone="orange" label="Trap: Memory-mapped I/O is not virtual memory">
Do not confuse memory-mapped I/O with virtual memory or memory-mapped files. Virtual memory uses the MMU to translate program addresses into physical DRAM pages. Memory-mapped I/O assigns physical hardware bus addresses to the silicon registers of network cards, GPUs, and disk controllers.
</Callout>

## Asynchronous Handshaking Protocols

When two hardware units run on independent clocks, synchronous fixed-delay sampling fails. A **handshake** provides closed-loop coordination: neither side advances until the other explicitly acknowledges the current state.

In a classic two-wire, four-phase asynchronous handshake, communication relies on two control signals: `READY` (asserted by the sender) and `ACK` (asserted by the receiver).

<Handshake />

The sequence proceeds through four non-overlapping phases:

1. **Sender Asserts Data and Request**: The sender places stable data bits onto the bus lines and raises `READY` (meaning: "data is valid on the wires").
2. **Receiver Latches and Acknowledges**: The receiver senses the rising edge of `READY`, reads the data lines into its internal latch, and raises `ACK` (meaning: "I have captured the data").
3. **Sender Releases Request**: The sender observes `ACK`, releases the data bus, and drops `READY` (meaning: "I know you received it; I am clearing the lines").
4. **Receiver Clears Acknowledge**: The receiver detects that `READY` is low and drops `ACK` (meaning: "the bus is clear, ready for the next transaction").

Because each edge triggers the next, this protocol operates correctly across any cable length and with arbitrary speed differences between sender and receiver.

## Three Ways to Move Data

Architectures transfer data between peripherals and memory using three distinct methods, trading hardware complexity against CPU utilization.

<IoMethods />

### 1. Programmed I/O (Polling)

Under **programmed I/O**, the CPU takes full responsibility for moving every byte. To read data, the processor writes a read command to the controller's command register, and then enters a tight software loop reading the status register over and over.

This repetitive testing is called **polling** or busy-waiting. The CPU asks: "Is the data ready? Is the data ready?" until the `READY` bit turns to 1. The CPU then reads the byte from the controller data register, writes it into a memory address, increments the pointer, and repeats.

Polling is simple to implement and requires zero specialized interrupt hardware. However, it wastes almost all CPU cycles when applied to slow or unpredictable devices. A 3 GHz processor polling a keyboard that produces 10 characters per second wastes 300 million clock cycles between every keystroke.

<Callout tone="violet" label="When is polling actually the fastest choice?">
High-speed networking drivers using kernel-bypass frameworks (like DPDK) intentionally disable interrupts and use dedicated polling loops. When a 100 Gbps network card receives 14 million packets per second, an interrupt would arrive every 70 nanoseconds. The overhead of context switching and saving registers would completely overwhelm the CPU. Polling eliminates interrupt overhead when packets arrive continuously.
</Callout>

### 2. Interrupt-Driven I/O

To eliminate busy-waiting, **interrupt-driven I/O** delegates the waiting to the hardware device. The CPU issues a command to the peripheral controller and immediately returns to running other application threads.

When the peripheral finishes gathering data or becomes ready for the next byte, its controller asserts an **interrupt request** (`IRQ`) line connected to the processor.

```
CPU Execution:
  Instruction N  -->  Instruction N+1  -->  [ Hardware Interrupt! ]
                                                     |
                                                     v
                                            Save PC & PSW to Stack
                                                     |
                                                     v
                                            Jump to Vector in IVT
                                                     |
                                                     v
                                            Execute ISR Body (Read Data)
                                                     |
                                                     v
                                            Execute IRET (Restore State)
                                                     |
                                                     v
                                        Resume Instruction N+2
```

At the boundary between instructions, the CPU checks its interrupt pins. If interrupts are enabled, the hardware takes over:

1. **Context Preservation**: The CPU finishes the current instruction, pushes the [program counter](/courses/computer-architecture/ripple-and-synchronous-counters#the-program-counter) and Processor Status Word (PSW/Flags) onto the system stack, and disables further maskable interrupts.
2. **Vector Lookup**: The CPU determines which device interrupted by reading an **interrupt vector** (an index into an Interrupt Vector Table / IVT in low memory).
3. **ISR Execution**: The CPU jumps to the target **Interrupt Service Routine** (ISR), which reads the byte from the controller, stores it in memory, and clears the controller's interrupt flag.
4. **State Restoration**: The ISR ends with an interrupt return instruction (`IRET`), popping the saved registers and PC, allowing the suspended application to resume transparently.

#### Handling Multiple Devices: Priority and Arbitration

When several devices interrupt simultaneously, the CPU must prioritize them:

- **Software Polling**: All devices share a single interrupt pin. The ISR polls each controller's status register in software priority order. This is simple, but servicing lower-priority devices suffers high latency.
- **Daisy-Chained Priority**: The CPU sends an Interrupt Acknowledge signal ($\overline{\text{INTA}}$) down a serial chain through all controllers. The first controller with a pending interrupt intercepts the signal and places its unique vector number onto the data bus. Downstream devices are blocked until the upstream device finishes.
- **Programmable Interrupt Controllers (PIC)**: Dedicated silicon, such as the Intel 8259A or modern ARM Generic Interrupt Controller (GIC), accepts distinct IRQ lines from multiple peripherals. An internal [priority encoder](/courses/logic-design/comparators-decoders-encoders#priority-encoders) selects the highest-priority request, delivers its vector to the CPU, and enables nested preemption so high-priority real-time events preempt low-priority background handlers.

### 3. Direct Memory Access (DMA)

Interrupt-driven I/O works well for low-rate peripherals like keyboards, but it collapses on high-throughput devices. Transferring a 4 KB disk block byte-by-byte via interrupts requires 4,096 separate interrupt cycles. Each interrupt forces register saves, pipeline stalls, and cache flushes, consuming thousands of CPU cycles for a tiny amount of useful work.

**Direct Memory Access** (**DMA**) solves this by introducing a specialized hardware coprocessor: the **DMA controller** (**DMAC**). The CPU offloads the entire block transfer to the DMAC, freeing the processor to execute unrelated code while data flows directly between the peripheral and system RAM.

#### Internal Architecture of a DMA Controller

A DMA controller contains four primary registers:

1. **Memory Address Register (MAR)**: Holds the physical starting address in DRAM where data will be read or written. The DMAC automatically increments (or decrements) this register after every word transfer.
2. **Word Count Register (WCR)** (or byte counter): Holds the number of words remaining in the block transfer. The DMAC decrements this register after each transfer.
3. **Control Register**: Holds bits specifying transfer direction (device-to-memory vs. memory-to-device), word width (8, 16, 32, or 64 bits), and transfer mode.
4. **Status Register**: Reports transfer progress, error status, and the `TC` (Terminal Count) flag.

```
Transfer Flow:
1. CPU programs DMAC (Address, Count, Direction).
2. DMAC asserts HOLD (Bus Request) to CPU.
3. CPU floats bus pins and asserts HLDA (Bus Grant).
4. DMAC drives bus lines: asserts MEMW and IOR simultaneously.
   Data moves from I/O Controller directly to DRAM.
5. Word Count decrements to zero.
6. DMAC releases bus and asserts IRQ to CPU.
```

#### DMA Transfer Modes

A DMA controller can access the system bus in three different modes:

- **Burst Mode (Block Mode)**: The DMAC takes control of the bus and transfers the entire block of data in one continuous operation without releasing the bus. This delivers maximum transfer throughput, but it blocks the CPU from accessing main memory for the entire duration of the burst.
- **Cycle Stealing**: The DMAC grabs the bus, transfers a single data word, and immediately releases the bus back to the CPU for one or more cycles. It "steals" an occasional memory cycle from the CPU, interleaving I/O and processor work with minimal CPU disruption.
- **Transparent Mode (Hidden DMA)**: The DMAC monitors the CPU clock phases and only transfers data during clock cycles when the CPU is executing internal register-to-register ALU operations and is guaranteed not to use the external memory bus. This achieves zero CPU slowdown, but requires complex timing synchronization logic.

#### Scatter-Gather DMA

Modern operating systems use [virtual memory](/courses/computer-architecture/virtual-memory#pages-frames-and-address-decomposition), allocating physical memory in scattered, non-contiguous 4 KB page frames. A 64 KB file buffer that appears contiguous in virtual memory is physically fragmented across 16 different DRAM frames.

Traditional DMA controllers can only transfer a single physically contiguous block. To handle fragmented memory, modern controllers use **scatter-gather DMA**:

```
Descriptor Table in Memory:
[ Descriptor 0 ]: Physical Address: 0x1A000, Length: 4096 --> Next Descriptor: 0x50000
[ Descriptor 1 ]: Physical Address: 0x3F000, Length: 4096 --> Next Descriptor: 0x50020
[ Descriptor 2 ]: Physical Address: 0x82000, Length: 4096 --> Next Descriptor: NULL
```

The CPU builds a linked list of buffer descriptors in memory, each containing a physical buffer pointer, byte length, and a pointer to the next descriptor. The DMA controller autonomously traverses this chain, loading descriptors and streaming non-contiguous physical pages into a continuous peripheral transfer without bothering the CPU between pages.

## DMA and Cache Coherence

Because a DMA controller bypasses the CPU and writes directly to main memory, it introduces a severe hardware hazard: the **cache coherence problem**.

Consider what happens in a system with a [write-back cache](/courses/computer-architecture/cache-policies#what-happens-on-a-write):

1. **DMA Output Hazard (Stale Memory)**: The CPU writes new data to a memory buffer. With a write-back cache, the modified data sits in the L1/L2 cache with its dirty bit set; main DRAM still holds the old data. If a DMA controller attempts to transmit that buffer to a network card, it reads the stale data from DRAM and sends corrupted data over the wire.
2. **DMA Input Hazard (Stale Cache)**: A network card receives a packet, and the DMA controller writes the bytes into DRAM. If the CPU already had that memory block loaded into its cache, the cache lines now contain old, obsolete data. When the CPU subsequently reads the buffer, it hits the cache and reads stale data, completely missing the newly arrived packet!

Architectures resolve this using two techniques:

- **Software Invalidation and Flushing**: The operating system kernel manually prepares cache lines before every DMA transfer. Before DMA output, the OS calls `clflush` or write-back instructions to force dirty lines to DRAM. Before reading DMA input, the OS invalidates matching cache lines, forcing the CPU to fetch fresh data from DRAM.
- **Hardware Bus Snooping (Coherent DMA)**: The DMA controller connects to a coherent bus interconnect (such as the PCIe Root Complex). When DMA writes to memory, the cache controllers snoop the transaction and automatically invalidate or update matching internal cache lines. When DMA reads from memory, a cache holding dirty data intervenes and supplies the fresh data directly.

## Comparison of I/O Transfer Methods

| Feature | Programmed I/O | Interrupt-Driven I/O | Direct Memory Access (DMA) |
|---|---|---|---|
| **Data Mover** | CPU | CPU | DMA Controller |
| **CPU Involvement** | 100% of transfer time | Setup + once per byte/word | Setup + once per block |
| **Hardware Complexity** | Minimal (no extra logic) | Moderate (interrupt lines, IVT) | High (DMAC, bus arbitration) |
| **Transfer Rate** | Limited by CPU polling loop | Limited by ISR context-switch latency | Maximum (limited only by bus bandwidth) |
| **Ideal Peripherals** | Dedicated real-time sensors, DPDK | Keyboards, mice, UART serial | NVMe SSDs, GPUs, Gigabit Ethernet |

## Exam-Style Practice

### Problem 1: Polling vs. Interrupt Overhead Analysis

<ModelAnswer>
**Problem:** A computer system has a 1 GHz CPU ($10^9$ clock cycles per second, clock cycle time $t = 1\text{ ns}$). A network interface controller receives network packets at a steady rate of $50,000\text{ packets/second}$.

1. **Part A (Polling):** The operating system polls the network controller at a frequency of $100,000\text{ times/second}$ (every $10\ \mu\text{s}$). Each polling check takes $30\text{ CPU cycles}$ when no packet is present, and $250\text{ cycles}$ to retrieve the packet when data is present. Calculate the total CPU cycles consumed per second and the percentage of CPU time spent on network I/O.
2. **Part B (Interrupts):** The system switches to interrupt-driven I/O. Servicing each interrupt requires $40\text{ cycles}$ of initial overhead (pipeline flush, context saving, and vector dispatch), $250\text{ cycles}$ to process the packet in the ISR, and $30\text{ cycles}$ for state restoration (`IRET`). Calculate the total CPU cycles consumed per second and the percentage of CPU time spent on network I/O.
3. **Part C (Crossover):** At what packet arrival rate (packets per second) does interrupt-driven I/O consume exactly the same amount of CPU time as the $100,000\text{ Hz}$ polling loop?

---

**Solution:**

**Part A: Polling Calculation**

The total number of polling attempts per second is $f_{\text{poll}} = 100,000\text{ polls/s}$.

The packet arrival rate is $R = 50,000\text{ packets/s}$.

- Polls finding a packet: $50,000\text{ polls/s} \times 250\text{ cycles} = 12,500,000\text{ cycles/s}$.
- Polls finding no packet: $(100,000 - 50,000)\text{ polls/s} \times 30\text{ cycles} = 50,000 \times 30 = 1,500,000\text{ cycles/s}$.

Total polling cycles per second:

$$C_{\text{poll}} = 12,500,000 + 1,500,000 = 14,000,000\text{ cycles/second}$$

CPU utilization:

$$\text{Utilization} = \frac{14,000,000\text{ cycles/s}}{1,000,000,000\text{ cycles/s}} \times 100\% = 1.4\%$$

The CPU spends $1.4\%$ of its computing capacity servicing the network interface under polling.

**Part B: Interrupt Calculation**

Each arriving packet generates exactly one interrupt. The total CPU cycles required per interrupt is:

$$C_{\text{intr}} = C_{\text{context}} + C_{\text{process}} + C_{\text{restore}} = 40 + 250 + 30 = 320\text{ cycles/packet}$$

At $50,000\text{ packets/s}$:

$$C_{\text{total\_intr}} = 50,000\text{ packets/s} \times 320\text{ cycles/packet} = 16,000,000\text{ cycles/second}$$

CPU utilization:

$$\text{Utilization} = \frac{16,000,000\text{ cycles/s}}{1,000,000,000\text{ cycles/s}} \times 100\% = 1.6\%$$

The CPU spends $1.6\%$ of its capacity on interrupts. Notice that at this high arrival rate, polling ($1.4\%$) is actually more efficient than interrupts ($1.6\%$) because it avoids context-switch overhead on every packet!

**Part C: Crossover Point**

Under the fixed $100,000\text{ Hz}$ polling routine, total cycles as a function of packet rate $R$ is:

$$C_{\text{poll}}(R) = (100,000 - R) \times 30 + R \times 250 = 3,000,000 + 220 R$$

Under interrupt-driven I/O, total cycles as a function of packet rate $R$ is:

$$C_{\text{intr}}(R) = 320 R$$

Equating the two:

$$320 R = 3,000,000 + 220 R$$
$$100 R = 3,000,000 \implies R = 30,000\text{ packets/second}$$

- If the packet rate is below $30,000\text{ packets/s}$, interrupt-driven I/O is more efficient.
- If the packet rate exceeds $30,000\text{ packets/s}$, polling consumes fewer CPU cycles.
</ModelAnswer>

### Problem 2: DMA Controller Transfer Timing and Bus Stealing

<ModelAnswer>
**Problem:** A storage controller uses DMA to transfer a $64\text{ KB}$ block ($65,536\text{ bytes}$) from an SSD controller buffer into main RAM. The system bus is $32\text{ bits}$ wide ($4\text{ bytes}$) and operates at $100\text{ MHz}$ ($10\text{ ns}$ clock period).

1. **Part A (Burst Mode):** In burst mode, acquiring the bus takes $4\text{ bus cycles}$, each 4-byte word transfer takes $1\text{ bus cycle}$, and releasing the bus takes $2\text{ bus cycles}$. The CPU requires $600\text{ CPU cycles}$ at $1\text{ GHz}$ to initialize the DMA registers, and $450\text{ CPU cycles}$ to handle the completion interrupt. Calculate the total time to transfer the entire block, the effective transfer throughput in megabytes per second (MB/s), and the total CPU time consumed.
2. **Part B (Comparison with Interrupts):** If the same $64\text{ KB}$ transfer were performed using interrupt-driven I/O moving $4\text{ bytes}$ per interrupt, and each interrupt required $60\text{ CPU cycles}$ of CPU processing time on the $1\text{ GHz}$ CPU, calculate the total CPU time required. How much CPU execution time does DMA save?

---

**Solution:**

**Part A: DMA Burst Mode**

1. Calculate the number of 4-byte words in the $64\text{ KB}$ block:

$$N_{\text{words}} = \frac{65,536\text{ bytes}}{4\text{ bytes/word}} = 16,384\text{ words}$$

2. Calculate the bus cycles required:

$$C_{\text{bus}} = C_{\text{acquire}} + (N_{\text{words}} \times 1) + C_{\text{release}} = 4 + 16,384 + 2 = 16,390\text{ bus cycles}$$

3. Calculate the bus transfer duration at $100\text{ MHz}$ ($t_{\text{bus}} = 10\text{ ns}$):

$$T_{\text{bus}} = 16,390 \times 10\text{ ns} = 163,900\text{ ns} = 163.90\ \mu\text{s}$$

4. Calculate CPU setup and completion interrupt time on the $1\text{ GHz}$ CPU ($t_{\text{cpu}} = 1\text{ ns}$):

$$C_{\text{cpu}} = 600 + 450 = 1,050\text{ cycles}$$
$$T_{\text{cpu}} = 1,050 \times 1\text{ ns} = 1,050\text{ ns} = 1.05\ \mu\text{s}$$

5. Total elapsed time for the transfer:

$$T_{\text{total}} = T_{\text{bus}} + T_{\text{cpu}} = 163.90\ \mu\text{s} + 1.05\ \mu\text{s} = 164.95\ \mu\text{s}$$

6. Effective throughput:

$$\text{Throughput} = \frac{65,536\text{ bytes}}{164.95 \times 10^{-6}\text{ s}} \approx 397,308,275\text{ B/s} \approx 378.91\text{ MB/s (binary)}$$

The CPU is occupied for only $1.05\ \mu\text{s}$ out of the entire $164.95\ \mu\text{s}$ transfer, leaving the CPU $99.36\%$ free to run user processes.

**Part B: Comparison with Interrupt-Driven Transfer**

Moving $65,536\text{ bytes}$ in 4-byte words requires:

$$N_{\text{interrupts}} = 16,384\text{ interrupts}$$

If each interrupt requires $60\text{ CPU cycles}$:

$$C_{\text{total\_cpu}} = 16,384 \times 60 = 983,040\text{ cycles}$$

At $1\text{ GHz}$ ($1\text{ ns}$ per cycle):

$$T_{\text{cpu\_interrupts}} = 983,040 \times 1\text{ ns} = 983.04\ \mu\text{s}$$

Under interrupt-driven I/O, the CPU spends $983.04\ \mu\text{s}$ actively executing interrupt service code.

**CPU Savings:**

$$\Delta T_{\text{cpu}} = 983.04\ \mu\text{s} - 1.05\ \mu\text{s} = 981.99\ \mu\text{s}$$

DMA reduces CPU overhead from $983.04\ \mu\text{s}$ down to $1.05\ \mu\text{s}$, delivering a $936\times$ reduction in CPU time consumed!
</ModelAnswer>
