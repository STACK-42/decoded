# Parallel Processing

During the 1980s and 1990s, processors grew faster mostly through higher clock speeds and deeper instruction pipelines. Computers sped up because single cores ran at higher frequencies.

Around 2004, that approach hit a physical wall. Chips became too hot to cool with ordinary fans and heatsinks. Transistors kept shrinking under Moore's law, but running them faster drew too much power. Instead of pushing a single core to higher frequencies, chip designers placed multiple complete processor cores on the same chip die.

**Parallel processing** breaks a program into separate pieces that run at the same time on multiple processing units. The alternative is **serial processing**, where one processor runs instructions one after another in order.

### Why chips went multicore

Most of the power consumed by CMOS digital circuits is **dynamic power**, the energy spent charging and discharging transistor gates each clock cycle:

$$
P_{\text{dynamic}} = \alpha \times C \times V^2 \times f
$$

Where:
- $\alpha$ is the activity factor (fraction of gates switching each clock cycle).
- $C$ is the capacitive load of the transistors and interconnect wires.
- $V$ is the operating supply voltage.
- $f$ is the clock frequency.

In 1974, Robert Dennard observed that as transistor dimensions shrink by a factor of $s \approx 0.7$ with each generation:
- Gate length and width shrink by $s$, reducing area to $s^2 \approx 0.5$ (doubling transistor density per chip, the basis of Moore's law).
- Capacitance shrinks to $sC$.
- Under **Dennard scaling**, operating voltage could drop by the same factor ($V \to sV$), allowing clock frequency to increase ($f \to f/s$).
- Power per transistor dropped by $s^2$: $P \to \alpha(sC)(sV)^2(f/s) = s^2 P$.
- Power density (power per square millimeter) stayed constant: $\frac{s^2 P}{s^2 A} = \text{constant}$.

For thirty years, Dennard scaling let engineers increase clock speeds every generation without overheating chips.

Around 2004, this rule broke down. Gate insulating layers had thinned to about $1.2\text{ nm}$ (only four or five atoms thick). Electrons began leaking through the thin gates even when turned off. Operating voltage could not safely drop below roughly $0.7\text{ V}$ without electrical noise corrupting logic levels.

With voltage stuck between $0.8\text{ V}$ and $1.1\text{ V}$, increasing clock frequency caused power and heat to climb sharply. Chips reached $100\text{ to }150\text{ W/cm}^2$, the cooling limit of copper heatsinks and air fans.

This limit is the **Power Wall**. Because a single core could no longer scale in frequency, designers added more cores. Two cores running at $2.0\text{ GHz}$ deliver roughly the same total throughput as a single core running at $4.0\text{ GHz}$, but operate at a lower voltage, cutting power by more than half.

## Flynn's taxonomy

In 1966, computer scientist Michael J. Flynn categorized all computer systems by examining two independent dimensions: the number of **instruction streams** and the number of **data streams**.

<FlynnTaxonomy />

This classification produces four fundamental architectural categories:

| Architecture | Description | Typical Hardware | Primary Application |
|---|---|---|---|
| **SISD** (Single Instruction, Single Data) | One instruction operates on one data item at a time | Classic uniprocessors (Intel 8086, classic single-core CPUs) | Legacy sequential algorithms |
| **SIMD** (Single Instruction, Multiple Data) | One control unit broadcasts a single instruction to multiple processing elements | Vector supercomputers, SSE/AVX/NEON extensions, GPUs | Graphics, audio, image processing, machine learning |
| **MISD** (Multiple Instruction, Single Data) | Multiple processors execute different instructions on the same data stream | Fault-tolerant redundant systems (Space Shuttle computers), systolic arrays | Spacecraft voting systems, experimental signal filtering |
| **MIMD** (Multiple Instruction, Multiple Data) | Multiple autonomous processors execute distinct instructions on distinct data streams | Multicore PCs, multi-socket enterprise servers, cloud clusters | Operating systems, servers, general parallel workloads |

MISD is rarely used in standard computing because executing multiple distinct instructions on a single stream of data is seldom useful. Its primary real-world application is fault-tolerant redundancy: in the Space Shuttle primary flight software, four independent computers executed different implementations of flight control logic on identical telemetry sensor data, voting on output actuator commands to survive software and hardware faults. Another example is systolic arrays, where data streams through an array of pipelined arithmetic cells that perform successive filtering stages.

## SIMD: one instruction, many values

Consider brightening a 4K digital photograph ($3840 \times 2160 = 8,294,400\text{ pixels}$). Adding a brightness constant to every pixel on a traditional scalar (SISD) processor requires looping over eight million pixels:

```c
for (int i = 0; i < 8294400; i++) {
    pixels[i] += brightness;
}
```

This scalar loop requires over eight million instruction fetches, eight million instruction decodes, eight million pointer increments, and eight million branch evaluations. Over $90\%$ of the energy is wasted fetching and decoding the very same addition opcode repeatedly.

A **SIMD** architecture eliminates this overhead. A single instruction fetch and decode controls dozens or hundreds of arithmetic units operating in lockstep on wide register vectors.

<SimdDemo />

SIMD architectures take three primary hardware forms:

1. **Vector processors**: Pipelined vector arithmetic units that operate on continuous arrays streamed from memory or vector registers (such as the classic Cray-1).
2. **Short-vector / Multimedia extensions**: Wide registers (128-bit, 256-bit, or 512-bit) embedded directly inside standard CPU cores. Examples include Intel AVX-512 (which operates on sixteen 32-bit floats in a single cycle) and ARM NEON.
3. **Graphics Processing Units (GPUs)**: Massive SIMD arrays deployed under a Single Instruction, Multiple Threads (**SIMT**) execution model. A modern GPU integrates thousands of arithmetic cores organized into streaming multiprocessors. Hardware schedulers group threads into lockstep clusters (called **warps** of 32 threads on NVIDIA, or **wavefronts** of 64 threads on AMD), applying the same instruction across thousands of data points concurrently. This makes GPUs well suited for deep learning and matrix multiplication.

### The penalties: memory stride and branch divergence

SIMD hardware reaches peak efficiency only when code satisfies two architectural constraints:

1. **Unit-stride memory access**: When vector elements reside in contiguous memory locations, the memory controller fetches an entire 64-byte cache line in a single burst, populating the vector register immediately. If data is stored with non-unit strides or scattered randomly in memory, the processor must execute hardware **gather** (loading individual addresses into a vector register) or **scatter** (writing vector elements to disparate addresses) instructions. Gather and scatter serialize memory operations into multiple separate cache lookups, which drops SIMD throughput.
2. **Branch divergence**: Because all 32 threads in a warp share a single instruction decoder, they must execute identical instructions in lockstep. If threads evaluate an `if-else` condition with differing outcomes, the GPU cannot execute both paths simultaneously. Instead, the hardware serializes execution: it first runs the `if` body while deactivating threads whose condition was false using an execution mask, and then runs the `else` body while deactivating threads whose condition was true. If threads diverge evenly, execution throughput drops by half.

## MIMD: independent workers

**MIMD** systems use multiple independent processor cores, each with its own program counter, instruction decoder, and execution datapath.

### Shared memory vs. distributed memory

MIMD hardware falls into two main structural topologies:

1. **Shared-memory systems**: All processors access a unified physical address space:
   - **Symmetric Multiprocessing (SMP) / Uniform Memory Access (UMA)**: Multiple processors connect to a centralized main memory through a shared system bus or crossbar switch. Access latency to any memory location is identical for every CPU (typically around $60\text{ ns}$).
   - **Non-Uniform Memory Access (NUMA)**: Memory is physically partitioned among processor sockets, but remains unified under a single global address space. A CPU accesses its local socket memory rapidly ($\approx 60\text{ ns}$), while accessing remote memory across point-to-point coherent interconnects (such as Intel Ultra Path Interconnect [UPI] or AMD Infinity Fabric) takes longer ($\approx 140\text{ ns}$). Operating system thread schedulers must be NUMA-aware, pinning threads to the specific socket where their data structures reside.
2. **Distributed-memory systems (clusters)**: Independent computers (nodes) connected over a high-speed network (such as InfiniBand or 100 GbE). Each node has its own private address space; processors coordinate exclusively by sending explicit messages across the network (using protocols like MPI).

### Hardware multithreading

To keep execution datapaths busy when an instruction stalls on memory latency, processors employ **hardware multithreading**:

- **Fine-grained multithreading**: The processor switches between execution threads on every single clock cycle in a round-robin schedule, hiding latency bubbles but slowing single-thread speed.
- **Coarse-grained multithreading**: The processor executes one thread until a major stall event occurs (such as an L3 cache miss), then switches to an alternate thread.
- **Simultaneous Multithreading (SMT / Hyper-Threading)**: A superscalar core replicates architectural registers (Program Counter, register file) while sharing functional ALUs and caches. When Thread 0 is waiting for a memory load, Thread 1 issues instructions to the idle ALUs during the very same clock cycle. An 8-core CPU with SMT presents itself to the operating system as 16 logical processors.

### Coherence vs. consistency

Multiprocessor memory design separates two distinct concepts:

- **Cache Coherence**: Guarantees that all processors observe a consistent view of writes to the **same memory address**. It answers: "What value does a read to address $X$ return after a write to address $X$?"
- **Memory Consistency**: Defines the legal ordering of reads and writes across **different memory addresses**. It answers: "In what order do writes to address $X$ and address $Y$ become visible to other cores?" While cache coherence is enforced by hardware protocols like MESI, memory consistency requires memory models (such as Sequential Consistency, Total Store Ordering, or Weak Ordering) and explicit software fence instructions (`MFENCE` or `DMB`).

### The cache coherence problem and the MESI protocol

When multiple CPU cores each have a private Level 1 cache and share main memory, a severe consistency challenge emerges: the **cache coherence problem**.

If Core A and Core B both cache address `0x1000` (value 42), and Core A writes value 99 to that address, Core B's cache holds stale data. If Core B reads `0x1000`, it receives 42 instead of the updated 99.

To maintain coherence, multicore processors use **bus snooping protocols**, where each cache controller continuously monitors ("snoops") the coherent bus for transactions involving memory blocks it holds.

Modern processors use **write-invalidate** protocols: writing to a shared cache block invalidates other copies rather than updating them. This saves interconnect bandwidth because repeated writes to the same local variable do not flood the bus with data updates.

The industry-standard **MESI protocol** (also known as the Illinois protocol) assigns every cache block one of four states:

| State | Name | Meaning | Is Block Dirty? | Can Other Caches Hold It? |
|---|---|---|---|---|
| **M** | Modified | The cache block is present only in this cache and has been modified (dirty relative to DRAM). Must be written back to memory when evicted. | Yes | No |
| **E** | Exclusive | The cache block is present only in this cache and is clean (matches DRAM). Can be written silently without bus activity. | No | No |
| **S** | Shared | The cache block may be present in other CPU caches. It is clean (matches DRAM). Writing requires broadcasting an invalidation. | No | Yes |
| **I** | Invalid | The cache line does not contain valid data. Reading it causes a cache miss. | No | N/A |

Some architectures (such as AMD Opteron/EPYC and ARM) extend MESI to **MOESI** by adding an **Owner (O)** state. In MOESI, a core holding a dirty line can share read-only copies with other caches without first writing the block back to slow DRAM; the Owner core retains responsibility for eventually writing the modified data back to memory when evicted.

### MESI state transitions

- **Read on state I (Read Miss)**: The core broadcasts a `BusRd` request on the bus.
  - If no other core holds the block, it transitions to **Exclusive (E)**.
  - If another core holds the block in E or S, it transitions to **Shared (S)**.
  - If another core holds the block in Modified (M), that core intercepts the request, flushes the dirty data to memory, transitions to Shared (S), and the requesting core loads the data into **Shared (S)**.
- **Write on state S (Write Upgrade)**: The core broadcasts an `Invalidate` signal on the bus. All other caches containing the block transition to **Invalid (I)**. The writing core transitions from **Shared to Modified (M)**.
- **Write on state E (Silent Upgrade)**: Because the block is present exclusively in this cache, the core transitions to **Modified (M)** with zero bus communication.
- **Write on state I (Write Miss)**: The core issues a `BusRdX` (Read with Intent to Modify) request. All other caches invalidate their copies, and the writing core loads the block directly into **Modified (M)**.

## Levels of parallelism

Modern computing exploits parallelism across multiple structural tiers simultaneously:

| Level | Granularity | Managed By | Physical Mechanism |
|---|---|---|---|
| **Bit-level** | 8-bit to 64-bit words | Chip hardware | Word-wide ALUs, 64-bit adders |
| **Instruction-level (ILP)** | Individual assembly instructions | Hardware & Compiler | Pipelining, out-of-order execution, superscalar issue |
| **Data-level (DLP)** | Arrays, vectors, matrices | Programmer & Compiler | SIMD vector registers, GPU streaming multiprocessors |
| **Thread-level (TLP)** | Independent concurrent threads | Operating System | Multicore chips, Simultaneous Multithreading (SMT) |
| **Task / Process-level** | Independent programs, services | Distributed software | Cloud server clusters, high-performance computing (HPC) |

## The limit: Amdahl's law

If adding cores makes computers faster, why not deploy 1,000 cores to make every program run 1,000 times faster?

In 1967, computer architect Gene Amdahl proved that the speedup achievable by parallel hardware is strictly bounded by the portion of the program that cannot be parallelized.

Amdahl's law considers a fixed problem size (**strong scaling**). Let $p$ be the fraction of the code that can run in parallel ($0 \le p \le 1$), and $s = 1 - p$ be the inherently serial fraction that must run sequentially on a single core (such as reading input, initializing data structures, or synchronizing results).

The total execution time on 1 core is:

$$
T(1) = T_{\text{serial}} + T_{\text{parallel}} = (1 - p)T(1) + p T(1)
$$

On $N$ processor cores, the serial fraction still takes $(1 - p)T(1)$ because only one processor can execute it. The parallel fraction is divided among the $N$ cores:

$$
T(N) = (1 - p)T(1) + \frac{p T(1)}{N}
$$

The resulting speedup is the ratio of execution times:

$$
\text{Speedup} = \frac{T(1)}{T(N)} = \frac{T(1)}{(1 - p)T(1) + \dfrac{p T(1)}{N}} = \frac{1}{(1 - p) + \dfrac{p}{N}}
$$

As the number of processors $N$ grows toward infinity ($N \to \infty$), the term $\frac{p}{N}$ approaches zero:

$$
\lim_{N \to \infty} \text{Speedup} = \frac{1}{1 - p} = \frac{1}{s}
$$

Experiment with parallel fractions and core counts below. Observe the orange bar, representing the sequential portion of the execution time: no matter how many cores are added, the orange bar never shrinks.

<AmdahlLab />

If a program is $90\%$ parallel ($p = 0.90$, meaning $s = 0.10$ is serial), the maximum theoretical speedup on an infinite number of processors is:

$$
\text{Speedup}_{\max} = \frac{1}{1 - 0.90} = \frac{1}{0.10} = 10\times
$$

Even with 10,000 cores, speedup cannot exceed $10\times$ because the 10% sequential portion sets an upper limit.

### Gustafson's law: weak scaling

Amdahl's law assumes that problem size remains fixed as computing resources expand. In practice, researchers do not use supercomputers to solve the same problem faster; they use more cores to solve much larger problems that were previously intractable (such as simulating weather at 1-kilometer grid resolution instead of 100-kilometer resolution).

In 1988, John Gustafson formulated **scaled speedup** (**weak scaling**), where problem size expands proportionally with processor count so that parallel execution time remains constant:

Let the execution time on the parallel system be normalized to $1$:

$$
T_{\text{parallel}} = s + (1 - s) = 1
$$

On a sequential uniprocessor, executing this larger scaled workload requires running the serial work once and the parallel work $N$ times:

$$
W(N) = s + N(1 - s)
$$

The scaled speedup is:

$$
\text{Speedup}_{\text{Gustafson}} = \frac{W(N)}{T_{\text{parallel}}} = s + N(1 - s) = N - s(N - 1)
$$

Where $s$ is the serial fraction of the parallel program.

Under Gustafson's law, if $s = 0.15$ on $N = 64$ processors, the scaled speedup is:

$$
\text{Speedup} = 64 - 0.15 \times (64 - 1) = 64 - 9.45 = 54.55\times
$$

Parallel efficiency under Gustafson scaling is:

$$
\text{Efficiency} = \frac{\text{Speedup}}{N} = \frac{N - s(N - 1)}{N} = 1 - s \left( \frac{N - 1}{N} \right)
$$

As $N \to \infty$, efficiency never drops below $1 - s$ ($85\%$ efficiency for $s = 0.15$), regardless of how many cores are added.

Amdahl's law governs execution when you want a fixed task completed as fast as possible; Gustafson's law governs execution when you want to accomplish the maximum amount of work within a fixed time budget.

## Traps and pitfalls

<Callout tone="orange" label="Trap: Amdahl's law does not make parallel computing futile">
Amdahl's law is sometimes seen as proof that large multicore systems are not worth building. But Amdahl's law applies to fixed problem sizes (strong scaling). When problem size grows along with core count (weak scaling), Gustafson's law applies, and efficiency stays high.
</Callout>

<Callout tone="orange" label="Trap: False sharing causes cache thrashing without shared data">
**False sharing** happens when two threads on different cores update separate variables that sit inside the same 64-byte cache line. The threads never touch each other's data, but the coherence protocol invalidates the entire line on every write, creating bus contention. Programmers fix this by padding independent variables to separate 64-byte boundaries.
</Callout>

<Callout tone="orange" label="Trap: Confusing cache coherence with memory consistency">
A multicore chip with MESI cache coherence does not automatically run multithreaded programs in sequential order. Cache coherence guarantees only that all cores agree on updates to any single address. It gives no guarantee about the order of writes to different addresses. Memory barriers (`MFENCE` or `DMB`) are required to enforce cross-address ordering.
</Callout>

<Callout tone="orange" label="Trap: The GPU throughput trap">
Running code on a GPU does not automatically make it faster. GPUs achieve high throughput on parallel, branch-free code with contiguous memory access. For sequential code, pointer-heavy data structures, or diverging branches, a modern CPU core runs faster than a GPU shader core.
</Callout>

<Callout tone="violet" label="Architectural synthesis: The unifying principle of computer design">
Pipelining, caches, virtual memory, and multicore parallelism all tackle the same issue: computation is faster than communication. By overlapping work, caching active data, and splitting tasks across cores, processor architectures turn memory latency into useful throughput.
</Callout>

## Worked practice problems

### Problem 1: Amdahl's law and multicore scaling analysis

A software company analyzes a database query engine and determines that $85\%$ of the execution time can be parallelized across multiple cores ($p = 0.85$). The remaining $15\%$ consists of sequential lock synchronization and transaction log writing ($s = 0.15$).

Calculate:
1. The theoretical speedup and parallel efficiency ($\text{Speedup} / N \times 100\%$) when running on an 8-core processor.
2. The theoretical speedup and parallel efficiency when running on a 64-core enterprise server.
3. The asymptotic speedup limit as the number of cores approaches infinity ($N \to \infty$).
4. The parallel fraction $p$ required to achieve an actual speedup of $20\times$ on any processor count.
5. The scaled speedup under Gustafson's law for $N = 64$ cores with a serial fraction of $s = 0.15$.

<ModelAnswer>
**Part 1: Speedup and efficiency on 8 cores:**

$$p = 0.85, \quad s = 1 - p = 0.15, \quad N = 8$$

$$\text{Speedup}_8 = \frac{1}{(1 - p) + \dfrac{p}{N}} = \frac{1}{0.15 + \dfrac{0.85}{8}} = \frac{1}{0.15 + 0.10625} = \frac{1}{0.25625} \approx 3.9024$$

Parallel efficiency on 8 cores:

$$\text{Efficiency}_8 = \frac{\text{Speedup}_8}{N} \times 100\% = \frac{3.9024}{8} \times 100\% \approx 48.78\%$$

---

**Part 2: Speedup and efficiency on 64 cores:**

$$\text{Speedup}_{64} = \frac{1}{0.15 + \dfrac{0.85}{64}} = \frac{1}{0.15 + 0.01328125} = \frac{1}{0.16328125} \approx 6.1244$$

Parallel efficiency on 64 cores:

$$\text{Efficiency}_{64} = \frac{\text{Speedup}_{64}}{N} \times 100\% = \frac{6.1244}{64} \times 100\% \approx 9.57\%$$

Increasing cores by a factor of 8 (from 8 to 64) only yields an increase in speedup from $3.90\times$ to $6.12\times$ because the 15% serial fraction dominates.

---

**Part 3: Asymptotic speedup limit:**

$$\text{Speedup}_{\max} = \frac{1}{1 - p} = \frac{1}{0.15} \approx 6.6667$$

Even with an infinite number of processor cores, this program can never achieve more than a $6.67\times$ speedup on a fixed workload.

---

**Part 4: Parallel fraction required for 20× speedup:**

The asymptotic speedup ceiling must be at least 20:

$$\text{Speedup}_{\max} = \frac{1}{1 - p} \ge 20 \implies 1 - p \le \frac{1}{20} = 0.05 \implies p \ge 0.95$$

To achieve a $20\times$ speedup on any number of processors, at least $95\%$ of the code must be parallelized.

---

**Part 5: Gustafson scaled speedup on 64 cores:**

Under weak scaling (problem size scales with core count):

$$\text{Speedup}_{\text{Gustafson}} = N - s(N - 1) = 64 - 0.15 \times (64 - 1) = 64 - 0.15 \times 63 = 64 - 9.45 = 54.55$$

$$\text{Efficiency}_{\text{Gustafson}} = \frac{54.55}{64} \times 100\% \approx 85.23\%$$

Under Gustafson's law, the system achieves a $54.55\times$ speedup with over $85\%$ parallel efficiency.
</ModelAnswer>

### Problem 2: MESI cache coherence state trace

Consider a symmetric multiprocessor with three processor cores (Core 0, Core 1, and Core 2) connected via a shared snooping bus to main memory. Each core maintains a private cache implementing the 4-state MESI protocol.

Initially, cache block address `X` is not present in any cache (all three cores are in state **Invalid** for block `X`).

Trace the state of block `X` in each core's cache and record the resulting bus transactions for the following sequential operations:
1. **Core 0 reads address `X`**.
2. **Core 1 reads address `X`**.
3. **Core 0 writes address `X`**.
4. **Core 2 reads address `X`**.

<ModelAnswer>
**Step 1: Core 0 reads address `X`**
- Prior states: Core 0: `I`, Core 1: `I`, Core 2: `I`.
- Action: Core 0 misses and broadcasts a `BusRd` transaction on the bus.
- Snooping: Neither Core 1 nor Core 2 holds block `X`.
- Data supplier: Main memory supplies the block to Core 0.
- Transition: Because no other cache holds the line, Core 0 transitions to **Exclusive (E)**.
- Next states: Core 0: **`E`**, Core 1: **`I`**, Core 2: **`I`**.

---

**Step 2: Core 1 reads address `X`**
- Prior states: Core 0: `E`, Core 1: `I`, Core 2: `I`.
- Action: Core 1 misses and broadcasts a `BusRd` transaction on the bus.
- Snooping: Core 0 detects the read request for a block it holds in state `E`. Core 0 asserts the shared line on the bus and downgrades its state to **Shared (S)**.
- Data supplier: Main memory (or Core 0 via cache-to-cache transfer) supplies the block.
- Transition: Core 1 loads the block and transitions to **Shared (S)**.
- Next states: Core 0: **`S`**, Core 1: **`S`**, Core 2: **`I`**.

---

**Step 3: Core 0 writes address `X`**
- Prior states: Core 0: `S`, Core 1: `S`, Core 2: `I`.
- Action: Core 0 holds the line in `S`. To write without causing data inconsistency, it broadcasts an **`Invalidate`** transaction on the bus.
- Snooping: Core 1 detects the invalidation signal for block `X` and transitions its copy from `S` to **Invalid (I)**.
- Data supplier: Local cache (Core 0 modifies its local copy in place).
- Transition: Core 0 transitions from `S` to **Modified (M)**.
- Next states: Core 0: **`M`**, Core 1: **`I`**, Core 2: **`I`**.

---

**Step 4: Core 2 reads address `X`**
- Prior states: Core 0: `M`, Core 1: `I`, Core 2: `I`.
- Action: Core 2 misses and broadcasts a `BusRd` transaction on the bus.
- Snooping: Core 0 snoops the read request and sees that it owns the block in state `M` (dirty). Core 0 signals the bus to wait, flushes the dirty block data onto the bus (updating main memory and supplying the data to Core 2), and transitions from `M` to **Shared (S)**.
- Data supplier: **Core 0** (supplies the modified data directly via bus flush).
- Transition: Core 2 captures the data from the bus and transitions to **Shared (S)**.
- Next states: Core 0: **`S`**, Core 1: **`I`**, Core 2: **`S`**.
</ModelAnswer>
