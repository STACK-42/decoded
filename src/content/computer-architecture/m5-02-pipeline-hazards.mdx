# Pipeline Hazards

A pipeline works best when instructions flow through the datapath without stopping. In real programs, instructions depend on earlier results and share hardware. A **pipeline hazard** is any condition that prevents the next instruction from running in its scheduled clock cycle.

When a hazard occurs, the hardware or compiler must stall the pipeline, inserting empty cycle slots called **bubbles** (or **NOPs**). Hazards fall into three main categories:

1. **Structural hazards**: Hardware conflicts where multiple instructions need the same physical unit at the same time.
2. **Data hazards**: Dependencies where an instruction needs a result from an earlier instruction that has not finished yet.
3. **Control hazards**: Branch decisions where the address of the next instruction is not known yet.

## Structural hazards

A **structural hazard** happens when the hardware cannot run all requested operations at once because two instructions need the same physical unit.

A classic example occurs when a processor uses one memory port for both instructions and data. Look at the pipeline at cycle 4:

| Cycle | Instruction 1 | Instruction 2 | Instruction 3 | Instruction 4 |
|---|---|---|---|---|
| **Cycle 4** | `MEM` (accesses data) | `EX` (arithmetic) | `ID` (decode) | `IF` (fetches instruction) |

At cycle 4, Instruction 1 is in the Memory (MEM) stage reading or writing data, while Instruction 4 is in the Fetch (IF) stage reading an instruction word from memory. If memory has only one port, it cannot do both at once. One instruction must wait, inserting a bubble into the IF stage.

### Fixing structural hazards

Designers fix structural hazards by duplicating hardware:

1. **Separate instruction and data caches (Harvard architecture)**: Modern chips use separate Level 1 caches for instructions (I-Cache) and data (D-Cache). The IF stage reads instructions from the I-Cache while the MEM stage reads or writes data in the D-Cache at the same time over separate buses.
2. **Multi-ported register files**: The register file is built with multiple independent ports: two read ports so ID can read two operands, and one write port so WB can write a result during the same cycle.
3. **Duplicate functional units**: High-speed processors include multiple ALUs, dedicated multipliers, and separate address generation units.

## Data hazards

A **data hazard** occurs when the pipeline attempts to read an operand register before a preceding instruction has completed writing its result to that register.

In 1966, computer scientist Arthur Bernstein formulated the conditions for deterministic parallel execution. Let $I_k$ represent an instruction, $R(I_k)$ be the set of registers read by $I_k$ (the input set), and $W(I_k)$ be the set of registers written by $I_k$ (the output set).

Two instructions $I_1$ and $I_2$ (where $I_1$ comes before $I_2$ in program order) can run at the same time or out of order without altering the result if and only if all three of Bernstein's conditions hold:

1. $W(I_1) \cap R(I_2) = \emptyset$ (**Read-After-Write / RAW / True Dependency**): Instruction $I_2$ must not read a register written by $I_1$. Instruction $I_2$ requires the computed result of $I_1$. This is a true data dependency: data flows from one instruction to the next, so renaming registers cannot eliminate it.
2. $R(I_1) \cap W(I_2) = \emptyset$ (**Write-After-Read / WAR / Anti-Dependency**): Instruction $I_2$ must not overwrite a register before $I_1$ finishes reading it. In a simple in-order 5-stage pipeline, WAR never causes an error because $I_1$ reads in stage 2 (ID) before $I_2$ writes in stage 5 (WB). But WAR becomes a real hazard in processors that execute instructions out of order.
3. $W(I_1) \cap W(I_2) = \emptyset$ (**Write-After-Write / WAW / Output Dependency**): Instruction $I_2$ must not overwrite a register before $I_1$ writes to it. In an in-order pipeline, writes always finish in program order. But WAW hazards occur when stages have different lengths (for example, a 1-cycle integer add next to a 15-cycle floating-point divide).

WAR and WAW are **name dependencies** (or false dependencies). They exist only because the program reused a register name ($R_1$). Out-of-order processors eliminate them with **register renaming**, which maps program register names to a larger pool of physical registers.

Consider this RAW dependency sequence:

```assembly
ADD R1, R2, R3     ; R1 = R2 + R3 (writes R1 in stage 5: WB)
SUB R4, R1, R5     ; R4 = R1 - R5 (reads R1 in stage 2: ID)
```

Without hardware support, `SUB` enters ID at cycle 2 and reads $R_1$, but `ADD` does not write its sum to $R_1$ until cycle 5 (WB). Without a fix, `SUB` uses an outdated value.

### Resolving RAW data hazards

Hardware and software use four main techniques to resolve RAW data hazards:

#### 1. Hardware interlocking (stalling)

A circuit called the **Hazard Detection Unit** watches register addresses during decode. When a source register ($rs_1$ or $rs_2$) in ID matches the destination register ($rd$) of an instruction in EX, MEM, or WB, the unit stalls the pipeline:

- It disables the $PC$ write line so the program counter does not advance.
- It disables the `IF/ID` write line to keep the waiting instruction in ID.
- It sets control signals to zero in `ID/EX`, sending a harmless NOP bubble down the remaining stages.

Without forwarding, the `ADD`/`SUB` sequence needs **two stall cycles** before `SUB` can read the new value.

#### 2. Data forwarding (bypassing)

The idea behind **data forwarding** (or **bypassing**) is simple: the ALU produces its result at the end of stage 3 (EX). That value is already available two cycles before it is written back to the register file in stage 5 (WB).

Instead of waiting for write-back, the hardware adds bypass wires and multiplexers to the ALU inputs. The **Forwarding Unit** compares register numbers and sets the multiplexers:

- **EX Hazard forwarding**: If `EX/MEM.RegWrite` is true, `EX/MEM.RegisterRd != 0`, and `EX/MEM.RegisterRd == ID/EX.RegisterRs1`, the ALU result is forwarded straight from `EX/MEM` into the ALU input. This needs **0 stall cycles**.
- **MEM Hazard forwarding**: If `MEM/WB.RegWrite` is true, `MEM/WB.RegisterRd != 0`, and `MEM/WB.RegisterRd == ID/EX.RegisterRs1`, the value is forwarded from `MEM/WB` to the ALU input.
- **Priority rule**: If both an EX hazard and a MEM hazard involve the same register, the unit forwards from `EX/MEM`, which holds the newer value.
- **Register 0 check**: Checking `RegisterRd != 0` ensures writes to register 0 (always zero in MIPS and RISC-V) do not trigger false forwards.

The cycle-by-cycle execution table below shows how forwarding eliminates stalls between arithmetic instructions:

| Instruction | Cycle 1 | Cycle 2 | Cycle 3 | Cycle 4 | Cycle 5 | Hardware Action |
|---|---|---|---|---|---|---|
| `ADD R1, R2, R3` | IF | ID | EX | MEM | WB | ALU generates sum at end of EX (cycle 3) |
| `SUB R4, R1, R5` | | IF | ID | EX | MEM | Forwarded directly from `EX/MEM` to ALU input (0 stalls) |

#### 3. The load-use hazard: the unavoidable stall

Forwarding eliminates stalls between arithmetic instructions, but cannot eliminate the stall after a memory load. This is a **load-use hazard**.

```assembly
LW  R1, 0(R2)      ; Load R1 from memory (data arrives at end of stage 4: MEM)
ADD R3, R1, R4     ; Needs R1 at the start of stage 3: EX
```

Data from memory is only ready at the end of the MEM stage (cycle 4). The `ADD` instruction needs $R_1$ at the start of its EX stage (cycle 4). Getting the data to EX on time would require sending it backward in time, which hardware cannot do.

So the processor must insert a **1-cycle load-use stall**. The Hazard Detection Unit tests:

$$
\text{if } (\text{ID/EX.MemRead} \land ((\text{ID/EX.RegisterRd} == \text{IF/ID.RegisterRs1}) \lor (\text{ID/EX.RegisterRd} == \text{IF/ID.RegisterRs2})))
$$

When this condition is true, the Hazard Detection Unit holds `ADD` in ID for one cycle. In cycle 5, the loaded word is forwarded from the `MEM/WB` pipeline register directly into the ALU input:

| Instruction | Cycle 1 | Cycle 2 | Cycle 3 | Cycle 4 | Cycle 5 | Cycle 6 | Hardware Action |
|---|---|---|---|---|---|---|---|
| `LW R1, 0(R2)` | IF | ID | EX | MEM | WB | | Data read from cache available at end of MEM (cycle 4) |
| `ADD R3, R1, R4` | | IF | ID | ID (stall) | EX | MEM | Stalls 1 cycle in ID; forwarded from `MEM/WB` to EX in cycle 5 |

#### 4. Compiler instruction scheduling

Optimizing compilers eliminate load-use stalls in software by reordering independent instructions. If the compiler identifies an unrelated instruction located later in the code, it moves that instruction into the slot immediately following the load:

```assembly
; Unoptimized (1 stall cycle):
LW  R1, 0(R2)
ADD R3, R1, R4     ; Stalls 1 cycle waiting for R1
SUB R6, R7, R8     ; Independent instruction

; Scheduled by compiler (0 stall cycles):
LW  R1, 0(R2)
SUB R6, R7, R8     ; Executes during load memory latency
ADD R3, R1, R4     ; R1 is now ready in MEM/WB; forwarded with 0 stalls!
```

## Control hazards

A **control hazard** (or **branch hazard**) happens when the processor cannot tell which instruction to fetch next until a branch condition resolves.

Consider a conditional branch:

```assembly
BEQ R1, R2, target ; If R1 == R2, branch to target
ADD R4, R5, R6     ; Fetched in cycle 2: should this instruction execute?
```

In a standard 5-stage pipeline, `BEQ` fetches in cycle 1, decodes in cycle 2, and evaluates the register comparison ($R_1 == R_2$) and target address calculation in cycle 3 (EX).

If the processor waits until cycle 3 to discover whether the branch is taken, two instructions (`ADD` and the instruction after it) have already entered the pipeline. If the branch is taken, those two instructions were fetched incorrectly and must be discarded (**flushed**), wasting 2 clock cycles.

### Moving branch resolution to the ID stage

Processors reduce branch penalty by moving the branch evaluation hardware earlier in the pipeline. Adding a dedicated comparator and target address adder into the ID stage (cycle 2) resolves the decision at the end of cycle 2. This reduces the branch penalty from 2 cycles down to **1 cycle**.

### Branch handling strategies

Hardware and software use four main strategies to handle control hazards:

#### 1. Static branch prediction

The hardware uses a fixed rule without tracking past history:

- **Predict Not Taken**: The CPU always fetches the next sequential instruction ($PC + 4$). If the branch is not taken, execution continues with zero stall cycles. If the branch is taken, the fetched instruction in `IF/ID` is flushed, incurring a 1-cycle penalty.
- **Directional prediction**: Backward branches (negative offsets, which typically form loops) are predicted taken; forward branches (positive offsets, which typically handle `if-else` blocks or error checks) are predicted not taken.

#### 2. Delayed branching

Used in early RISC architectures (like MIPS and SPARC): the instruction located immediately after the branch in memory (the **branch delay slot**) always runs, whether the branch is taken or not. The compiler schedules an independent instruction into the delay slot, transforming the wasted flush cycle into productive work.

#### 3. Dynamic branch prediction

Real programs contain branches whose outcomes change dynamically. **Dynamic branch prediction** uses history tables in hardware to forecast branch directions:

- **1-bit predictor**: Remembers a single bit (Taken or Not Taken) for each branch address. In a loop that executes 10 times, a 1-bit predictor mispredicts twice: once when exiting the loop, and once on the first iteration when the loop is entered again. Accuracy is only $80\%$.
- **2-bit saturating counter**: Requires two consecutive mistakes to change its prediction. It operates as a 4-state finite state machine:

| State | Name | Prediction | Next State if Taken | Next State if Not Taken |
|---|---|---|---|---|
| **11** | Strongly Taken | Taken | 11 | 10 (Weakly Taken) |
| **10** | Weakly Taken | Taken | 11 (Strongly Taken) | 01 (Weakly Not Taken) |
| **01** | Weakly Not Taken | Not Taken | 10 (Weakly Taken) | 00 (Strongly Not Taken) |
| **00** | Strongly Not Taken | Not Taken | 01 (Weakly Not Taken) | 00 |

When exiting a loop, the 2-bit counter moves from Strongly Taken (11) to Weakly Taken (10). When the loop runs again, it still predicts Taken, achieving over $90\%$ accuracy on loop-heavy workloads.

#### 4. Branch Target Buffer (BTB) and Return Address Stack (RAS)

Even if a branch predictor correctly forecasts that a branch is taken during the IF stage, the processor still does not know the target address until the instruction is decoded.

A **Branch Target Buffer** (**BTB**) is a high-speed cache indexed by the current instruction $PC$. Each entry stores the predicted target address and history bits. If the current $PC$ hits in the BTB and the branch is predicted taken, the processor fetches the target address on the very next clock cycle, achieving a **0-cycle branch penalty**.

Function returns (`RET` or `JR $ra`), however, confuse a BTB. A common helper like `strlen` or `memcpy` is called from hundreds of different program locations. A BTB entry caches only the return destination of the most recent caller. When alternating callers invoke the same function, a BTB mispredicts the return address nearly every time.

To solve this, processors implement a hardware **Return Address Stack** (**RAS**):
- When a subroutine call instruction (`CALL` or `JAL`) is fetched in IF, the address of the next sequential instruction ($PC + 4$) is pushed onto the top of the RAS.
- When a subroutine return instruction (`RET` or `JR $ra`) is fetched in IF, the hardware pops the predicted return address directly from the top of the RAS.

Because subroutine calls and returns naturally follow Last-In, First-Out (LIFO) call nesting, a small 16-entry to 32-entry RAS predicts return addresses with over $99\%$ accuracy.

## The real CPI

In an ideal pipeline with no resource contention, no data stalls, and no mispredicted branches, the processor retires one instruction every clock cycle: $\text{CPI}_{\text{ideal}} = 1.0$.

Pipeline hazards increase the actual Cycles Per Instruction ($\text{CPI}$):

$$
\text{CPI} = \text{CPI}_{\text{ideal}} + \text{Stall}_{\text{structural}} + \text{Stall}_{\text{data}} + \text{Stall}_{\text{control}}
$$

Let:
- $f_{\text{load}}$ be the fraction of load instructions.
- $p_{\text{load\_use}}$ be the probability that a load is followed immediately by a dependent instruction without compiler scheduling (each incurring a 1-cycle load-use stall).
- $f_{\text{branch}}$ be the fraction of branch instructions.
- $p_{\text{mispredict}}$ be the branch misprediction rate.
- $c_{\text{penalty}}$ be the misprediction flush penalty in cycles.

$$
\text{CPI} = 1.0 + (f_{\text{load}} \times p_{\text{load\_use}} \times 1) + (f_{\text{branch}} \times p_{\text{mispredict}} \times c_{\text{penalty}})
$$

## Traps and pitfalls

<Callout tone="orange" label="Trap: Forwarding does not eliminate the load-use hazard stall">
Forwarding eliminates all stalls between back-to-back arithmetic instructions (`ADD` followed by `SUB`). However, forwarding cannot eliminate the stall between a memory load (`LW`) and its immediate dependent consumer because data from memory only becomes available at the end of the MEM stage. The hardware must insert at least one stall cycle unless the compiler separates the instructions.
</Callout>

<Callout tone="orange" label="Trap: 1-bit branch predictors thrash on loop boundaries">
A 1-bit branch predictor changes its prediction on every single misprediction. For any loop, it mispredicts both on loop exit and on the first iteration of the subsequent execution. A 2-bit saturating counter prevents this thrashing by absorbing the loop termination misprediction without switching its prediction polarity.
</Callout>

<Callout tone="orange" label="Trap: Confusing the BTB with the Branch History Table (BHT)">
Students frequently confuse branch direction prediction with branch target calculation. The Branch History Table (BHT) or 2-bit saturating counter predicts the direction (whether the branch is taken or not taken). The Branch Target Buffer (BTB) predicts the target address (where the branch jumps if taken). To achieve a zero-cycle branch penalty in stage 1 (IF), both structures must work together: the BHT predicts whether to jump, and the BTB supplies the target address before the opcode is decoded.
</Callout>

<Callout tone="orange" label="Trap: Confusing structural hazards with data hazards">
A structural hazard is a conflict over physical hardware resources (such as two instructions attempting to access a single memory port in the same cycle). A data hazard is a dependency between computed values (such as an instruction needing the result of an earlier calculation). Adding extra hardware units (like separate instruction and data caches) eliminates structural hazards, but can never eliminate true data dependencies (RAW).
</Callout>

<Callout tone="orange" label="Trap: Branch delay slot dependencies">
In architectures with branch delay slots (such as classic MIPS), the instruction in the delay slot executes unconditionally. A frequent mistake is placing an instruction in the delay slot that modifies the registers being compared by the branch. The branch comparison uses the register values from before the branch executes; modifying those registers in the delay slot does not change the branch decision, which confuses developers debugging assembly code.
</Callout>

<Callout tone="violet" label="Real-world consequence: Speculative execution and Spectre">
To avoid branch stalls, modern processors use **speculative execution**: they guess branch directions and execute instructions ahead of time. If the guess is wrong, the processor rolls back register updates. But speculatively executed instructions still change cache lines. The **Spectre** vulnerability (2018) exploits this: malicious code tricks the CPU into speculatively reading private memory, then measures cache timing to recover the secret data.
</Callout>

## Worked practice problems

### Problem 1: Pipeline hazard identification and execution trace

Consider the following MIPS assembly code sequence:

```assembly
I1: ADD R1, R2, R3     ; R1 = R2 + R3
I2: LW  R4, 0(R1)      ; R4 = Memory[R1 + 0]
I3: SUB R5, R4, R6     ; R5 = R4 - R6
I4: OR  R7, R1, R8     ; R7 = R1 | R8
I5: BEQ R5, R7, loop   ; If R5 == R7, branch to loop
```

For this sequence:
1. Identify all data dependencies (RAW) and control dependencies between instructions.
2. Determine the total number of clock cycles required to execute this sequence in a 5-stage pipeline **without forwarding** (hardware stalls only, assuming registers can be read and written in the same cycle via two-phase clocking).
3. Determine the total number of clock cycles required to execute this sequence in a 5-stage pipeline **with full forwarding hardware** (assuming branch resolution occurs in stage 3, and the branch is not taken).
4. Show how an optimizing compiler can reschedule these instructions to eliminate all data hazard stalls with forwarding.

<ModelAnswer>
**Part 1: Dependency analysis:**

- **$I_1 \to I_2$ (RAW on $R_1$):** $I_1$ writes $R_1$; $I_2$ reads $R_1$ as the base address for memory load.
- **$I_2 \to I_3$ (RAW on $R_4$):** $I_2$ loads $R_4$ from memory; $I_3$ reads $R_4$ as an ALU operand. This is a **load-use hazard**.
- **$I_1 \to I_4$ (RAW on $R_1$):** $I_1$ writes $R_1$; $I_4$ reads $R_1$ as a logical operand.
- **$I_3 \to I_5$ (RAW on $R_5$):** $I_3$ writes $R_5$; $I_5$ reads $R_5$ for branch comparison.
- **$I_4 \to I_5$ (RAW on $R_7$):** $I_4$ writes $R_7$; $I_5$ reads $R_7$ for branch comparison.
- **Control dependency:** Instructions following $I_5$ depend on the outcome of the branch.

---

**Part 2: Execution without forwarding (stalls only):**

Without forwarding, an instruction cannot enter the ID stage to read an operand until the producing instruction completes WB in stage 5:

- $I_1$ writes $R_1$ in cycle 5 (WB). With two-phase clocking, $I_2$ can read $R_1$ in ID during cycle 5. Thus, $I_2$ stalls in ID during cycles 3 and 4 (2 stall cycles).
- $I_2$ writes $R_4$ in cycle 9 (WB). $I_3$ reads $R_4$ in ID during cycle 9, stalling in ID during cycles 7 and 8 (2 stall cycles).
- $I_3$ writes $R_5$ in cycle 13 (WB). $I_5$ needs $R_5$, stalling in ID during cycles 11 and 12 (2 stall cycles).
- Base unpipelined cycles for 5 instructions: $k + n - 1 = 5 + 5 - 1 = 9\text{ cycles}$.
- Total stall bubbles added: $2 + 2 + 2 = 6\text{ stall cycles}$.
- Total cycles without forwarding: $9 + 6 = 15\text{ clock cycles}$.

---

**Part 3: Execution with full forwarding:**

With forwarding:
- **$I_1 \to I_2$:** $I_1$ produces $R_1$ at the end of EX (cycle 3). $I_2$ needs $R_1$ in EX at cycle 4. Value is forwarded from `EX/MEM` to ALU input with **0 stalls**.
- **$I_2 \to I_3$ (Load-use hazard):** $I_2$ receives $R_4$ from data memory at the end of MEM (cycle 5). $I_3$ needs $R_4$ at the start of EX (cycle 5). This requires a **1-cycle load-use stall**. In cycle 6, $R_4$ is forwarded from `MEM/WB` to the ALU input.
- **$I_1 \to I_4$:** $I_1$ has already written back $R_1$; forwarded or read from register file with **0 stalls**.
- **$I_3 \to I_5$:** $I_3$ produces $R_5$ in EX (cycle 6). $I_5$ enters EX in cycle 8 (due to $I_4$ executing in cycle 7). The value is forwarded from `MEM/WB` with **0 stalls**.
- Total execution cycles: $5 + (5 - 1) + 1\text{ (load-use stall)} = 10\text{ clock cycles}$.

---

**Part 4: Compiler rescheduling:**

Notice that $I_4$ (`OR R7, R1, R8`) depends only on $R_1$ (which is already ready after $I_1$) and is completely independent of $I_2$ and $I_3$. The compiler moves $I_4$ into the load delay slot between $I_2$ and $I_3$:

```assembly
I1: ADD R1, R2, R3     ; Writes R1
I2: LW  R4, 0(R1)      ; Loads R4
I4: OR  R7, R1, R8     ; Scheduled in load delay slot! Independent of R4
I3: SUB R5, R4, R6     ; R4 is now available; forwarded with 0 stalls!
I5: BEQ R5, R7, loop   ; Evaluates branch
```

By placing $I_4$ in the delay slot, $R_4$ completes its MEM stage while $I_4$ executes in EX. When $I_3$ arrives at EX, $R_4$ is already available in the `MEM/WB` register. The code executes in **9 clock cycles** with **0 stall cycles**.
</ModelAnswer>

### Problem 2: Quantitative CPI evaluation with instruction mix and hazard stalls

An architectural team evaluates a 5-stage pipelined processor running a scientific benchmark with the following instruction mix:

- **ALU operations**: $45\%$ of all instructions (0 stalls with forwarding).
- **Data Loads (`LW`)**: $25\%$ of all instructions. Profiling indicates that $50\%$ of all load instructions are followed immediately by an instruction that consumes the loaded register (causing a 1-cycle load-use hazard stall).
- **Data Stores (`SW`)**: $10\%$ of all instructions (0 stalls).
- **Conditional Branches (`BEQ`/`BNE`)**: $20\%$ of all instructions. The processor uses a 2-bit branch predictor that achieves an $85\%$ prediction accuracy ($15\%$ misprediction rate). Branch resolution occurs in stage 3 (EX), incurring a 2-cycle flush penalty on misprediction.
- Assume structural stalls are 0 due to split L1 Harvard caches.

Calculate:
1. The average data hazard stall cycles per instruction.
2. The average control hazard stall cycles per instruction.
3. The effective CPI of the processor.
4. The pipeline efficiency ($\text{CPI}_{\text{ideal}} / \text{CPI}_{\text{actual}} \times 100\%$).
5. The speedup of this pipelined processor over an unpipelined multicycle implementation with an average CPI of $4.2$ running at the same clock frequency.

<ModelAnswer>
**Part 1: Average data hazard stall cycles per instruction:**

Data stalls arise exclusively from unhidden load-use hazards:

$$\text{Stall}_{\text{data}} = f_{\text{load}} \times p_{\text{load\_use}} \times \text{Stall Penalty}$$

$$\text{Stall}_{\text{data}} = 0.25 \times 0.50 \times 1\text{ cycle} = 0.125\text{ stall cycles/instruction}$$

---

**Part 2: Average control hazard stall cycles per instruction:**

Control stalls arise from branch mispredictions:

$$\text{Mispredict Rate} = 1.0 - 0.85 = 0.15\ (15\%)$$

$$\text{Stall}_{\text{control}} = f_{\text{branch}} \times p_{\text{mispredict}} \times \text{Mispredict Penalty}$$

$$\text{Stall}_{\text{control}} = 0.20 \times 0.15 \times 2\text{ cycles} = 0.060\text{ stall cycles/instruction}$$

---

**Part 3: Effective CPI:**

$$\text{CPI}_{\text{effective}} = \text{CPI}_{\text{ideal}} + \text{Stall}_{\text{data}} + \text{Stall}_{\text{control}} + \text{Stall}_{\text{structural}}$$

$$\text{CPI}_{\text{effective}} = 1.0 + 0.125 + 0.060 + 0 = 1.185\text{ cycles/instruction}$$

---

**Part 4: Pipeline efficiency:**

$$\text{Efficiency} = \frac{\text{CPI}_{\text{ideal}}}{\text{CPI}_{\text{effective}}} \times 100\% = \frac{1.0}{1.185} \times 100\% \approx 84.39\%$$

The processor operates at approximately $84.4\%$ of its theoretical peak throughput.

---

**Part 5: Speedup over unpipelined multicycle processor:**

At equal clock frequency, speedup is the ratio of CPIs:

$$\text{Speedup} = \frac{\text{CPI}_{\text{unpipelined}}}{\text{CPI}_{\text{pipelined}}} = \frac{4.2}{1.185} \approx 3.544$$

The pipelined processor achieves a $3.54\times$ speedup over the multicycle design.
</ModelAnswer>
