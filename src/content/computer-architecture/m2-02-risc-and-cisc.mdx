# RISC and CISC

In the early decades of computer engineering, memory was slow, expensive, and limited in capacity. Programmers wrote software by hand in assembly language, and early compilers struggled to generate efficient machine code. To make programming easier and conserve memory, hardware designers added complex instructions directly into processor hardware.

This created **Complex Instruction Set Computers** (CISC). The goal was to close the **semantic gap**, the conceptual distance between high-level programming language statements and machine instructions.

A single CISC instruction could perform several distinct actions: fetch two operands from memory, multiply them, and write the product back to RAM. The VAX-11/780 included instructions like `INDEX` to check array bounds and compute scaled offsets, and `POLY` to evaluate an entire polynomial in floating point with a single instruction. The x86 architecture features instructions like `REP MOVSB` to copy entire blocks of memory.

## The empirical shift

In the early 1980s, researchers including David Patterson at UC Berkeley and John Hennessy at Stanford measured how real compilers and software actually used these rich instruction sets.

The data revealed a consistent pattern known as the **80/20 rule**: approximately 80% of a processor's execution time was spent executing only 20% of its instructions. These frequent instructions were simple operations: integer additions, register copies, conditional branches, and basic memory loads and stores. The specialized instructions designed to close the semantic gap went largely unused by optimizing compilers.

Yet supporting those rare, complex instructions imposed heavy penalties on the entire machine:

1. **Longer clock periods**: The **critical path** is the longest sequence of combinational logic gates a signal must traverse between two clocked registers. In a synchronous processor, clock frequency is bounded by the slowest logic stage. When hardware decoders must handle up to 15 different instruction lengths, multiple prefix bytes, and complex addressing modes, the decode stage delay stretches out. Even when executing a 1-cycle integer addition, the CPU clock cannot tick faster than the worst-case decode delay allows.
2. **Silicon waste**: Vast areas of chip silicon were dedicated to microcode ROMs that stored execution routines for rarely used instructions.
3. **Pipelining bottlenecks**: **Pipelining** overlaps the execution of multiple instructions across sequential stages (fetch, decode, execute, memory, writeback), much like an assembly line in a factory. Instructions with variable lengths and unpredictable cycle counts stall the pipeline and make regular scheduling nearly impossible.

This led to **Reduced Instruction Set Computers** (**RISC**), which cut specialized instructions and simplified decoding so that common operations run as fast as possible.

<Callout tone="orange" label="Trap: Confusing instruction count with execution time">
A CISC compiler might emit 4 instructions where a RISC compiler emits 8 instructions for the exact same calculation, leading students to conclude that the CISC processor will finish faster. But execution time depends on three factors: $\text{Time} = IC \times CPI \times \tau$. If the CISC processor averages 6 cycles per instruction at a 1.0 GHz clock, and the RISC processor averages 1.2 cycles per instruction at a 2.5 GHz clock, the RISC machine executes the task in $8 \times 1.2 \times 0.4\text{ ns} = 3.84\text{ ns}$, while the CISC machine takes $4 \times 6 \times 1.0\text{ ns} = 24.0\text{ ns}$.
</Callout>

## Core principles of RISC

RISC is a design approach built around six technical principles:

1. **Load-store architecture**: Arithmetic and logical instructions operate exclusively on internal processor registers (`ADD R1, R2, R3`). Only two dedicated operations access system memory: `LOAD` to read from RAM into a register, and `STORE` to write from a register into RAM.
2. **Fixed instruction length**: Every instruction uses identical bit width, typically 32 bits. Instruction fields such as register addresses sit at fixed bit locations, allowing the processor to fetch operands from the register file before opcode decoding finishes.
3. **Single-cycle throughput**: By breaking complex operations into primitive steps, each instruction can advance through one stage of an execution pipeline per clock cycle. While each instruction takes several cycles of pipeline latency to complete, the processor retires one instruction every clock cycle under ideal conditions ($\text{CPI} \approx 1.0$).
4. **Hardwired control**: Instead of reading multi-step microcode from internal ROM, RISC processors generate control signals directly from combinational [logic gates](/courses/logic-design/logic-gates), cutting execution latency.
5. **Large general-purpose register file**: RISC processors provide 32 or more general-purpose registers. Holding variables in high-speed registers avoids frequent trips across the slow memory bus.
6. **Optimizing compilers**: Responsibility for efficiency shifts to the compiler, which schedules instructions to keep pipeline stages occupied and allocates registers to eliminate redundant memory traffic.

## Overlapping register windows

Procedure calls cost time on traditional architectures. Each time a program calls a function, it must save caller registers to memory, push arguments, jump to the callee, execute, and restore registers upon return.

To eliminate this memory bus traffic, the Berkeley RISC and SPARC architectures introduced **overlapping register windows**.

A SPARC processor might contain 128 physical hardware registers, but a program sees only 32 logical registers at any moment, designated $R_0$ through $R_{31}$. An internal hardware register called the **Current Window Pointer** ($CWP$) indicates the active window. These 32 registers are partitioned into four groups of 8:

- **Global registers** ($R_0 - R_7$): Shared by all procedures across the entire system.
- **Out registers** ($R_8 - R_{15}$): Hold arguments to pass when calling the next procedure.
- **Local registers** ($R_{16} - R_{23}$): Hold local variables private to the current procedure.
- **In registers** ($R_{24} - R_{31}$): Hold input arguments received from the caller.

When procedure $A$ calls procedure $B$, executing a `SAVE` instruction advances the window pointer (in SPARC, decrementing $CWP$ in circular modulo arithmetic, $CWP \leftarrow (CWP - 1) \bmod W$, matching downward stack growth; returning via `RESTORE` increments $CWP$). The active window slides by 16 physical registers: the `Out` registers of procedure $A$ ($R_8 - R_{15}$) directly become the `In` registers of procedure $B$ ($R_{24} - R_{31}$). Parameters are passed between functions without writing a single byte to memory, because both procedures reference the exact same physical storage cells.

When nested function calls exceed the capacity of the physical register file, the processor triggers a **window overflow trap**, prompting the operating system to spill the oldest window frame to system RAM.

<Callout tone="orange" label="Trap: Assuming register windows copy data across buses">
When procedure $A$ passes arguments to procedure $B$, no data moves across an internal bus. The processor updates the Current Window Pointer ($CWP$). The physical storage cells that hold procedure $A$'s $R_8$ are the exact same cells procedure $B$ accesses as $R_{24}$.
</Callout>

## Modern convergence

Today, the line between RISC and CISC has largely blurred:

1. **CISC chips run RISC underneath**: Modern x86 processors from Intel and AMD do not execute x86 instructions directly on the datapath. Instead, hardware decoders split incoming variable-length CISC instructions into fixed-size, primitive operations called **micro-operations** ($\mu\text{ops}$). These $\mu\text{ops}$ are executed by an internal out-of-order superscalar RISC core. Software enjoys x86 backwards compatibility, while hardware gains RISC pipelining efficiency.
2. **RISC chips adopted compression**: Early RISC programs suffered from poor code density compared to CISC. To conserve cache space and memory bandwidth, modern RISC architectures introduced 16-bit compressed instruction extensions, such as ARM Thumb-2 and the RISC-V `C` extension. A hardware predecoder expands these 16-bit instructions into standard 32-bit instructions during instruction fetch.

<Callout tone="orange" label="Trap: Equating RISC with reduced capability">
A Reduced Instruction Set Computer does not have less computational power than a CISC processor. Both architectures are Turing complete and run the same software. RISC reduces instruction format complexity, not what the machine can compute.
</Callout>

<Callout tone="orange" label="Trap: Believing modern x86 chips execute CISC instructions directly">
Modern x86 processors from Intel and AMD do not execute legacy CISC instructions directly on their arithmetic units. Instead, the CPU front end translates variable-length x86 instructions into fixed-length micro-operations ($\mu\text{ops}$) that execute on an internal RISC engine.
</Callout>

<ModelAnswer title="Problem 1: Assembly compilation comparison">
Consider the high-level language statement:

$$Y[i] = X[i] \times 4 + Z$$

Assume $i$ is stored in register `R1`, the base addresses of arrays $X$ and $Y$ are stored in registers `R2` and `R3`, and variable $Z$ resides in memory location `0x1000`. Each array element is a 4-byte integer.

Write the instruction sequences to evaluate this statement on:
1. A CISC architecture with register-memory operations and scaled indexed addressing.
2. A pure RISC load-store architecture.

Compare the total instruction count and the number of memory access operations.

---

**Solution:**

**1. CISC architecture:**
```asm
; Scale index i by 4 and load X[i], multiply by 4, add Z, store to Y[i]
MOV  EAX, [R2 + R1*4]     ; Load X[i] directly using scaled indexing
SHL  EAX, 2               ; Multiply by 4 (shift left by 2 bits)
ADD  EAX, [0x1000]        ; Add value of Z directly from memory
MOV  [R3 + R1*4], EAX     ; Store result directly into Y[i]
```
- Total instructions: 4.
- Memory accesses: 3 (Read $X[i]$, Read $Z$, Write $Y[i]$).

**2. RISC load-store architecture (using RISC-V style mnemonics where SLLI is Shift Left Logical Immediate):**
```asm
; All memory access strictly through explicit LOAD and STORE
SLLI R4, R1, 2            ; R4 = i * 4 (shift left by 2 bits for byte offset)
ADD  R5, R2, R4           ; R5 = address of X[i]
LOAD R6, [R5]             ; R6 = X[i]
SLLI R6, R6, 2            ; R6 = X[i] * 4
LOAD R7, [0x1000]         ; R7 = Z
ADD  R8, R6, R7           ; R8 = (X[i] * 4) + Z
ADD  R9, R3, R4           ; R9 = address of Y[i]
STORE [R9], R8            ; Store result into Y[i]
```
- Total instructions: 8.
- Memory accesses: 3 (Read $X[i]$, Read $Z$, Write $Y[i]$).

Both architectures perform the same number of memory data transfers (3 data references), but the CISC machine requires half as many instructions because its addressing hardware computes base-plus-scaled-index calculations in single instructions. The RISC machine executes more instructions, but each is simple enough to pipeline cleanly.
</ModelAnswer>

<ModelAnswer title="Problem 2: SPARC register window allocation">
A RISC processor with overlapping register windows has 136 physical hardware registers.

The register organization defines:
- 8 Global registers shared by all procedures.
- 24 registers per window (8 In, 8 Local, 8 Out).
- An overlap of 8 registers between adjacent windows (the Out registers of window $k$ serve as the In registers of window $k+1$).

1. Calculate how many distinct window frames ($W$) this physical register file supports.
2. Determine the maximum depth of procedure nesting possible before a window overflow trap occurs.

---

**Solution:**

**Part 1: Number of distinct window frames:**
First, subtract the dedicated global registers:
$$\text{Available registers} = 136 - 8 = 128$$

Each window requires 8 In, 8 Local, and 8 Out registers. Because the Out registers of one window overlap with the In registers of the next, each additional window consumes only 16 unique physical registers (8 Local + 8 Out, while its In registers reuse the previous window's Out registers).

The relationship for $W$ circular windows is:
$$\text{Total registers} = \text{Globals} + W \times 16$$
$$136 = 8 + 16W$$
$$16W = 128 \implies W = 8$$

The processor supports 8 complete register windows.

**Part 2: Maximum procedure nesting depth:**
Because the register windows form a circular ring buffer, one window must remain reserved to handle the trap condition when wrapping around. Therefore, the processor can execute up to 7 nested procedure calls ($W - 1 = 7$) before triggering a window overflow trap that forces the operating system to spill window contents to RAM.
</ModelAnswer>

<ModelAnswer title="Problem 3: Procedure call parameter passing overhead">
Compare the hardware overhead of a procedure call that passes 4 integer arguments and returns 1 integer result on two machines:

1. **CISC machine using memory stack frames:**
   - Caller pushes 4 arguments onto the memory stack (`PUSH`).
   - `CALL` instruction pushes the return address onto the stack.
   - Callee prologue pushes the old frame pointer (`EBP`) and updates `EBP`.
   - Callee executes, places return value in register `EAX`.
   - Callee epilogue pops the saved frame pointer (`POP EBP`).
   - `RET` instruction pops the return address.
   - Caller cleans up the 4 stack arguments.

2. **RISC machine with overlapping register windows:**
   - Caller writes 4 arguments directly into Out registers `R8-R11`.
   - `CALL` writes return address into link register `R15`.
   - `SAVE` instruction decrements the Current Window Pointer ($CWP$), mapping caller's Out registers directly to callee's In registers `R24-R27`.
   - Callee executes, places return value in In register `R24`.
   - `RESTORE` increments $CWP$, mapping callee's In register back to caller's Out register `R8`.
   - `RET` branches to return address.

Assume memory read/write operations take 3 clock cycles each, while internal register-to-register and pointer updates take 1 clock cycle. Calculate the total memory bus accesses and clock cycle overhead dedicated strictly to procedure linkage.

---

**Solution:**

**1. CISC stack frame overhead:**
- Pushing 4 arguments: 4 memory writes ($4 \times 3 = 12$ cycles).
- `CALL` pushing return address: 1 memory write (3 cycles).
- Prologue saving `EBP`: 1 memory write (3 cycles).
- Epilogue restoring `EBP`: 1 memory read (3 cycles).
- `RET` popping return address: 1 memory read (3 cycles).
- Callee argument cleanup: 1 cycle (adjusting stack pointer).
- Total memory bus references: $4 + 1 + 1 + 1 + 1 = 8$ memory transactions.
- Total linkage execution time: $12 + 3 + 3 + 3 + 3 + 1 = 25$ clock cycles.

**2. RISC register window overhead:**
- Loading arguments into Out registers: 4 internal register writes ($4 \times 1 = 4$ cycles).
- `CALL` saving link register: 1 cycle (internal register write).
- `SAVE` decrementing $CWP$: 1 cycle (internal pointer register update).
- Returning value into In register: 1 cycle (internal register write).
- `RESTORE` incrementing $CWP$: 1 cycle (internal pointer register update).
- `RET` branch: 1 cycle.
- Total memory bus references: 0 memory transactions.
- Total linkage execution time: $4 + 1 + 1 + 1 + 1 + 1 = 9$ clock cycles.

Register windows eliminate all 8 memory transactions to RAM, cutting linkage overhead from 25 cycles to 9 cycles while avoiding data cache pollution.
</ModelAnswer>

<ModelAnswer title="Problem 4: Window overflow and underflow trap cost analysis">
A SPARC processor incorporates $W = 8$ circular register windows. The operating system maintains a Window Invalid Mask ($WIM$), where bit $k = 1$ marks window $k$ as reserved to trap circular overflow.
An application executes a recursive function that reaches a call nesting depth of 14 before returning to depth 0.

1. At what call depth does the first Window Overflow trap occur?
2. If saving a window frame of 16 registers (8 Local + 8 In/Out) to system RAM requires 32 clock cycles, calculate the cumulative trap penalty incurred across the entire recursive execution (both call descent and return ascent).
3. Explain the mechanical roles of the Current Window Pointer ($CWP$) and Window Invalid Mask ($WIM$) during a trap.

---

**Solution:**

**Part 1: Initial overflow call depth:**
The processor starts with 1 window reserved for the trap handler boundary ($WIM$ bit set). With $W = 8$ windows, the hardware can accommodate $W - 1 = 7$ nested frames without accessing memory.
The 8th procedure call attempts to shift $CWP$ into the window guarded by $WIM = 1$, firing the first Window Overflow trap at call depth 8.

**Part 2: Cumulative trap penalty:**
- **Call descent (depth 8 to 14):**
  Calls at depths 8, 9, 10, 11, 12, 13, and 14 each trigger an overflow trap to spill an older window frame to the memory stack:
  $$\text{Overflow traps} = 14 - 8 + 1 = 7 \text{ traps}$$
  $$\text{Descent penalty} = 7 \times 32 \text{ cycles} = 224 \text{ clock cycles}$$

- **Return ascent (depth 14 returning back to depth 0):**
  As each procedure returns via `RESTORE`, $CWP$ moves in reverse. When $CWP$ steps into a window that was previously spilled to memory, a Window Underflow trap fires to restore the 16 registers from RAM:
  $$\text{Underflow traps} = 7 \text{ traps}$$
  $$\text{Ascent penalty} = 7 \times 32 \text{ cycles} = 224 \text{ clock cycles}$$

- **Total penalty:**
  $$\text{Total cycle cost} = 224 + 224 = 448 \text{ clock cycles}$$

**Part 3: Role of CWP and WIM:**
$CWP$ is a 3-bit hardware pointer indicating which physical register bank maps to the current procedure's local and parameter registers. $WIM$ is an 8-bit register where a single `1` bit marks the boundary. When a `SAVE` instruction causes $(CWP - 1) \bmod 8$ to match the $WIM$ bit position, hardware traps to OS kernel code. The kernel writes the targeted window to RAM and rotates the $WIM$ bit, permitting execution to continue safely.
</ModelAnswer>

<ModelAnswer title="Problem 5: Code expansion and instruction cache working set">
A software suite contains 100,000 instructions when compiled for a CISC architecture with an average instruction length of 3.2 bytes. The identical source code compiled for a 32-bit fixed-length RISC architecture requires 140,000 instructions.

1. Calculate the binary code size in kilobytes for both architectures.
2. If both processors are equipped with a 64 KB L1 instruction cache, compare their working set coverage and explain the performance dilemma RISC architectures encounter.
3. How do modern compressed instruction set extensions (such as ARM Thumb-2 or RISC-V "C") resolve this dilemma?

---

**Solution:**

**Part 1: Binary code size:**
- CISC binary size:
  $$\text{Size}_{\text{CISC}} = 100{,}000 \times 3.2\text{ bytes} = 320{,}000\text{ bytes} \approx 312.5\text{ KB}$$
- RISC binary size (fixed 32-bit = 4 bytes):
  $$\text{Size}_{\text{RISC}} = 140{,}000 \times 4.0\text{ bytes} = 560{,}000\text{ bytes} \approx 546.9\text{ KB}$$
- Code size ratio:
  $$\frac{560{,}000}{320{,}000} = 1.75\times$$
The RISC executable is 75% larger.

**Part 2: Instruction cache impact:**
A 64 KB cache holds:
- In CISC: $\dfrac{65{,}536\text{ bytes}}{3.2\text{ bytes/instruction}} \approx 20{,}480\text{ instructions}$.
- In RISC: $\dfrac{65{,}536\text{ bytes}}{4.0\text{ bytes/instruction}} = 16{,}384\text{ instructions}$.

The CISC cache holds 25% more instructions. If a program's hot inner loop contains 18,000 instructions, it fits entirely within the CISC L1 cache (zero cache misses), but exceeds the RISC cache capacity, triggering frequent L1 cache misses and memory stall penalties that can negate the RISC processor's lower average CPI.

**Part 3: Compressed instruction sets:**
Compressed ISAs (like ARM Thumb-2 and RISC-V "C") introduce 16-bit encodings for the most common instructions (loads, stores, branches, simple arithmetic). The compiler mixes 16-bit and 32-bit instructions in the same binary without manual mode switches. A simple hardware expander in the fetch stage decompresses 16-bit instructions into standard 32-bit RISC operations before decoding, reducing binary size by 25% to 30% without sacrificing pipeline simplicity.
</ModelAnswer>

<ModelAnswer title="Problem 6: CISC micro-operation decomposition">
An x86 processor fetches the complex memory-to-register CISC instruction:

```asm
ADD [EAX + EBX*4 + 0x20], ECX
```

1. Decompose this single macro-instruction into its equivalent sequence of primitive RISC micro-operations ($\mu\text{ops}$).
2. Trace the data dependencies between the generated $\mu\text{ops}$.
3. Explain why this internal decomposition allows modern CISC processors to achieve pipelined execution with an effective CPI approaching 1.0.

---

**Solution:**

**Part 1: Micro-operation breakdown:**
The hardware instruction decoder splits the single macro-instruction into 4 atomic $\mu\text{ops}$:
```text
1. AGEN  T1, EAX, EBX, 4, 0x20 ; Address Generation Unit: T1 = EAX + (EBX * 4) + 0x20
2. LOAD  T2, [T1]             ; Memory Unit: Read 32-bit value at address T1 into temp reg T2
3. ADD   T3, T2, ECX          ; ALU: Add contents of T2 and ECX, store in temp reg T3
4. STORE [T1], T3             ; Memory Unit: Write sum T3 back to address T1
```

**Part 2: Data dependency analysis:**
- $\mu\text{op}$ 2 (LOAD) depends on $\mu\text{op}$ 1 (AGEN) for the target address $T_1$.
- $\mu\text{op}$ 3 (ADD) depends on $\mu\text{op}$ 2 (LOAD) for operand $T_2$.
- $\mu\text{op}$ 4 (STORE) depends on both $\mu\text{op}$ 1 (for address $T_1$) and $\mu\text{op}$ 3 (for result data $T_3$).

**Part 3: Architectural performance benefit:**
By converting the variable-length, multicycle CISC instruction into standardized, fixed-width $\mu\text{ops}$, the CPU core can execute them using a high-frequency RISC out-of-order execution engine. The execution units (ALU, Load Unit, Store Unit, AGU) can schedule independent $\mu\text{ops}$ from surrounding instructions in parallel, hiding memory latencies and achieving throughput of multiple instructions per clock cycle.
</ModelAnswer>
