# Buses and Arbitration

Inside a computer, thousands of hardware functional units must communicate. Connecting every component to every other component with dedicated point-to-point wires would require millions of traces, quickly consuming all available silicon area and motherboard layers. Instead, computers share communication highways called **buses**. Because a bus is a shared highway, it requires strict electrical conventions and traffic rules so signals do not collide.

## What is a Bus?

A **bus** is a shared communication pathway consisting of parallel conductors that connect two or more hardware devices. A bus line carries binary voltage signals representing $0$ or $1$.

```
+--------------------------------------------------------------+
| Control Lines: MEMR, MEMW, IOR, IOW, Clock, Reset, Ready...   |
+--------------------------------------------------------------+
| Address Lines: A0 to A31 (selects location or port)          |
+--------------------------------------------------------------+
| Data Lines:    D0 to D63 (transfers instructions and data)   |
+--------------------------------------------------------------+
        |                 |                 |
  +-----v-----+     +-----v-----+     +-----v-----+
  |    CPU    |     |   Memory  |     |    DMA    |
  +-----------+     +-----------+     +-----------+
```

A system bus comprises three distinct functional signal groups:

1. **Data Lines**: Transmit instructions, memory words, and I/O data words. The number of data lines is the **bus width** (such as 32 or 64 lines), which determines how many bytes move in a single transfer.
2. **Address Lines**: Specify the physical source or destination address of the data. An $n$-line address bus selects among $2^n$ distinct memory bytes or I/O ports. A 32-bit address bus addresses $4\text{ GB}$ of space, while a 48-bit bus addresses $256\text{ TB}$.
3. **Control Lines**: Coordinate access and operation across the shared lines. Control lines include read/write command strobes, clock signals, reset lines, bus request/grant lines, interrupt lines, and wait state indicators.

### The Electrical Problem of Shared Lines

When multiple chips connect to the same metal wire, two chips driving conflicting voltages at the same time (one driving $3.3\text{ V}$ and another driving $0\text{ V}$) create a low-resistance short circuit, drawing destructive currents and corrupting data.

To prevent this, every device connects to the shared bus lines through a [tri-state buffer](/courses/logic-design/memory-unit#tri-state-logic-and-shared-system-buses). A tri-state buffer has three possible output states: logic 1 (high voltage), logic 0 (low voltage), and high impedance (Hi-Z). When a device is inactive, its bus interface sits in the Hi-Z state, electrically disconnecting it from the wire and allowing another active device to drive the bus cleanly.

## The Physical Limits of Wide Parallel Buses

Early personal computers routed all components through a single, wide parallel backplane bus (such as ISA, VME, or early PCI). As processors accelerated from megahertz to gigahertz frequencies, shared parallel buses ran into severe physical barriers:

1. **Capacitive Loading**: Every device attached to a multi-drop bus adds parasitic capacitance. This capacitance increases the RC time constant of the trace, rounding off square voltage transitions and capping maximum clock frequencies.
2. **Clock Skew**: In a 64-bit parallel bus, slight differences in trace lengths, dielectric thickness, and crosstalk mean that 64 bits transmitted simultaneously arrive at the receiver at slightly different times. When clock frequencies exceed a few hundred megahertz, this **clock skew** exceeds the clock cycle time, corrupting data words.
3. **Bus Contention**: A single bus forces fast graphics cards, memory controllers, and slow keyboards to compete for the same physical wires.

```
Why Serial Replaced Parallel:

Wide Parallel Bus (32 traces):
Bit 0: -------------> (arrives at t = 0 ps)
Bit 1: --------------> (arrives at t = 40 ps)  <-- Clock Skew destroys data
Bit 2: ------------> (arrives at t = -20 ps)

Switched Serial Interconnect (PCIe Differential Pair):
Tx+ / Tx- : ====[ Embedded Clock & Data Packets ]====>
Clock is encoded directly in the signal: ZERO clock skew!
```

### The Shift to Switched Serial Fabrics (PCIe)

Modern architectures resolved these physical limits by replacing wide, multi-drop parallel buses with high-speed, point-to-point **switched serial fabrics**, exemplified by PCI Express (PCIe):

- Instead of 32 or 64 shared copper traces, PCIe uses dedicated point-to-point differential signaling pairs (one transmit pair $\text{Tx}^+/\text{Tx}^-$ and one receive pair $\text{Rx}^+/\text{Rx}^-$ per lane).
- The clock is embedded directly into the data bitstream using line coding (such as 8b/10b or 128b/130b), eliminating clock skew between separate lines.
- Bandwidth scales linearly by grouping lanes ($\times 1, \times 4, \times 8, \times 16$). A PCIe 4.0 $\times 16$ connection delivers roughly $31.5\text{ GB/s}$ of full-duplex throughput.
- A central PCIe switch routes packetized messages directly between devices without broadcast contention.

### The Modern Interconnect Hierarchy

Today's computers organize communication in a hierarchy of specialized links connected by bridges:

- **Processor-Memory Interconnect**: Extremely short, point-to-point coherent interconnects (such as Intel UPI/QPI or AMD Infinity Fabric) operating at gigahertz frequencies directly between CPU sockets and memory controllers.
- **System Expansion Fabric**: PCIe links connecting graphics processors, NVMe SSDs, and high-speed network interfaces to the CPU Root Complex.
- **Peripheral Buses**: Low-speed serial buses (USB, SATA, SPI, I2C, UART) managed through a chipset (Platform Controller Hub / PCH).

## Bus Protocols and Timing: Synchronous vs. Asynchronous

The rules governing when an address is valid, when data is sampled, and how devices acknowledge transfers form the **bus protocol**.

### Synchronous Bus Timing

In a **synchronous bus**, every bus event is coordinated by the edges of a shared system clock. All devices on the bus must run at the same clock frequency or an integer divisor of it.

```
Clock:     |___/---\___/---\___/---\___/---\___/---\___/---|
Address:   |   [   Valid Address   ]                   |
Control:   |   [   Read Command    ]                   |
Ready:     |___________________________/-------\___________|
Data:      |                   [     Valid Data    ]   |
Cycle:     |    T1 (Address)   | T2 (Wait) | T3 (Data) |
```

Consider a synchronous memory read:

1. **Cycle 1 (Address Phase)**: The bus master places the memory address on the address bus and asserts the Read control signal on the rising clock edge.
2. **Cycle 2 (Access / Wait States)**: The memory device decodes the address and retrieves data. If the memory cannot access data within a single clock cycle, it pulls the `READY` (or `WAIT`) control line low. The CPU detects this and inserts **wait states** (idle clock cycles), waiting for memory to finish.
3. **Cycle 3 (Data Phase)**: Memory places the data word onto the data bus and asserts `READY`. The CPU latches the data on the next rising clock edge, completing the transaction.

Synchronous buses require minimal control logic and achieve very high throughput over short physical distances. However, they suffer from clock skew over long wires, and every transaction must run at the speed of the slowest participating device unless wait states are inserted.

### Asynchronous Bus Timing

In an **asynchronous bus**, there is no shared bus clock. Timing is controlled entirely by interlocking control signals using a four-phase [handshake](/courses/computer-architecture/io-methods#asynchronous-handshaking-protocols):

1. The bus master asserts the address and read lines.
2. The master asserts `Master Sync` (`MSYN` or Address Strobe), signaling that the address lines are valid and settled.
3. The slave device decodes the address, retrieves the requested data, drives the data bus, and asserts `Slave Sync` (`SSYN` or Data Acknowledge).
4. The master detects `SSYN`, captures the data into its internal registers, and deasserts `MSYN`.
5. The slave detects the release of `MSYN`, clears its data lines, and deasserts `SSYN`.

Asynchronous buses accommodate devices of wildly different speeds without wasting cycles, and they are immune to clock skew over long cables. However, the round-trip signal propagation and handshake edge detection add protocol overhead to every single transfer.

## Arbitration: whose turn is it?

In any multi-device computer, multiple components act as a **bus master**: an active unit capable of initiating data transfers. The CPU, multiple DMA controllers, graphics processors, and network cards can all demand bus access simultaneously.

If two bus masters drive the address or data lines at the same time, the signals collide, producing corrupt data and electrical faults. **Bus arbitration** is the hardware mechanism that decides which bus master gains control of the bus when multiple requests collide.

<BusArbiter />

An arbitration scheme balances three primary design goals:

1. **Priority**: Time-critical devices (like high-speed network interfaces or real-time video capture controllers with small buffers) must receive immediate bus access to prevent buffer overflow.
2. **Fairness**: Low-priority devices (such as background CPU processing) must not be starved of bus access indefinitely.
3. **Hardware Overhead**: The arbitration protocol should require minimal dedicated wires and simple silicon logic.

### 1. Daisy Chaining (Serial Grant)

In a **daisy chain** arbitration protocol, all bus masters share a single Bus Request (`BR`) line and a single Bus Busy (`BBUSY`) line. A single Bus Grant (`BG`) line leaves the central arbiter and loops serially through each device in sequence.

```
Arbiter ---> [ BG In ] Master 0 [ BG Out ] ---> [ BG In ] Master 1 [ BG Out ] ---> ...
   ^                                                                                  |
   +---------------------- Common Bus Request Line -----------------------------------+
```

- When one or more devices need the bus, they pull the common `BR` line active.
- The arbiter senses `BR` and asserts the `BG` signal.
- The `BG` signal enters Master 0 (the device physically closest to the arbiter).
- If Master 0 requested the bus, it intercepts the grant, refuses to pass `BG` down the chain, asserts `BBUSY`, and takes control of the bus.
- If Master 0 did not request the bus, it passes `BG` out to Master 1.
- The grant signal continues snaking through devices until it reaches the first requesting master.

**Trade-offs:** Daisy chaining uses only three control wires regardless of how many devices are attached, and the central arbiter is trivial. However, priority is fixed by physical slot position: Master 0 always wins. If Master 0 generates continuous requests, all downstream devices suffer from **starvation** (they never receive bus access). Furthermore, grant propagation delay increases linearly with the number of devices ($O(N)$), and if any device in the chain fails or is removed, the grant signal breaks for all downstream masters.

### 2. Centralized Parallel Arbitration

In **centralized parallel arbitration**, each individual bus master has dedicated, independent Bus Request ($\text{REQ}_i$) and Bus Grant ($\text{GNT}_i$) lines connected directly to a central arbiter chip.

```
          +-----------------------+
Master 0 <== REQ 0 / GNT 0 =====> |                       |
Master 1 <== REQ 1 / GNT 1 =====> |    Central Arbiter    |
Master 2 <== REQ 2 / GNT 2 =====> |   (Priority Logic)    |
Master 3 <== REQ 3 / GNT 3 =====> |                       |
          +-----------------------+
```

Because the arbiter sees every active request simultaneously, it can execute sophisticated prioritization algorithms:

- **Fixed Priority**: Requests pass through an internal [priority encoder](/courses/logic-design/comparators-decoders-encoders#priority-encoders) (e.g. Master 0 > Master 1 > Master 2). Real-time devices are guaranteed minimal latency, but low-priority masters can still starve under heavy loads.
- **Round-Robin (Rotating Priority)**: The arbiter maintains an internal pointer to the most recently served master, $k$. In the next arbitration cycle, priority begins at $(k + 1) \bmod N$. This guarantees perfect fairness: no device can be starved, and maximum waiting time is mathematically bounded to $(N - 1)$ transactions.
- **Dynamic Priority**: The operating system or hardware controller dynamically changes master priority levels by writing to configuration registers inside the arbiter.

Parallel arbitration completes decisions in a single clock cycle and isolates device failures. Its drawback is line overhead: connecting $N$ masters requires $2N$ dedicated control lines.

### 3. Distributed (Decentralized) Arbitration

**Distributed arbitration** eliminates the central arbiter chip entirely. All bus masters participate in the arbitration decision using shared control and priority identification lines.

A classic implementation is **wired-OR self-selection** (used in SCSI and CAN bus architectures):

- Each bus master is assigned a unique $k$-bit binary priority ID.
- When arbitration begins, each requesting master asserts its priority ID on a shared open-collector arbitration bus, bit by bit from most significant bit to least significant bit.
- Because the bus uses wired-AND (or wired-OR with active-low signals), if Master A drives a 0 onto line $j$, but detects that line $j$ is currently held at 1 by another device, Master A realizes that a higher-priority master is also competing.
- Master A immediately withdraws its lower-order priority bits and concedes the bus.
- The highest-priority master sees its full ID intact on the bus lines and claims ownership.

Distributed arbitration provides high reliability with zero single point of failure, but it requires arbitration logic in every device interface.

## Split-Transaction (Pipelined) Protocols

In a traditional synchronous or asynchronous bus transaction, a memory read holds the bus locked for the entire duration of the transfer:

$$\text{Total Bus Lock Time} = T_{\text{address}} + T_{\text{memory\_access\_latency}} + T_{\text{data}}$$

If main DRAM takes $50\text{ ns}$ to retrieve a cache block, the shared bus sits completely idle for dozens of clock cycles while the memory chips precharge and strobe row addresses. No other device can use the bus during this dead time.

A **split-transaction bus** (also called a **pipelined bus** or **disconnected bus protocol**) divides a single logical read into two distinct, independent bus transactions:

```
Traditional Bus Read:
Bus:  [ Address ]================== Idle Waiting ==================[ Data ]
Master locks bus for the entire memory access latency!

Split-Transaction Bus Read:
Bus:  [ Req 1 (Tag A) ][ Req 2 (Tag B) ][ Reply 1 (Tag A) ][ Reply 2 (Tag B) ]
Bus is immediately released during memory latency, multiplying throughput!
```

1. **Request Phase**: The master arbitrates for the bus, transmits the memory read command, the memory address, and a unique **Transaction Tag** (identifying the requesting master and buffer), and then **immediately releases the bus**!
2. **Idle Latency**: While DRAM accesses the rows internally, the bus is completely free for other processors, DMA controllers, and graphics units to transfer data.
3. **Reply Phase**: When DRAM finishes fetching the data, the memory controller arbitrates for the bus as a master. Once granted, it places the data word onto the data bus along with the matching Transaction Tag. The original requesting master recognizes its tag, captures the data, and completes the read.

By decoupling requests from responses, split-transaction buses dramatically increase effective bus bandwidth and prevent slow devices from bottlenecking high-speed processors.

## Comparison of Bus Arbitration Protocols

| Arbitration Scheme | Number of Control Lines | Decision Latency | Fairness | Fault Tolerance |
|---|---|---|---|---|
| **Daisy Chain** | 3 lines total | $O(N)$ propagation delay | Poor (distant devices starve) | Low (single broken pin breaks chain) |
| **Centralized Parallel (Fixed)** | $2N$ lines | 1 clock cycle | Poor (low priority starves) | High (isolated device failures) |
| **Centralized Parallel (Round-Robin)** | $2N$ lines | 1 clock cycle | Perfect (bounded wait time) | High (isolated device failures) |
| **Distributed (Self-Selection)** | $\log_2 N$ arbitration lines | Bitwise settling time | Flexible (ID dependent) | Maximum (no central point of failure) |

### Problem 1: Synchronous vs. Asynchronous Bus Bandwidth Analysis

<ModelAnswer>
**Problem:** A computer architecture supports both a synchronous bus and an asynchronous bus. The bus data path is $32\text{ bits}$ wide ($4\text{ bytes}$).

1. **Part A (Synchronous Single Word):** The synchronous bus operates at $66\text{ MHz}$ (clock period $T_{\text{cyc}} = 15.15\text{ ns}$). A single 4-byte read requires $1\text{ clock cycle}$ to transmit the address, $2\text{ clock cycles}$ of memory access latency (wait states), and $1\text{ clock cycle}$ for the slave to transfer the 4-byte data word. Calculate the total time required for a 4-byte read, the effective bandwidth in megabytes per second (decimal MB/s), and the bus transfer efficiency (data cycles divided by total cycles).
2. **Part B (Synchronous Burst Mode):** The memory controller is upgraded to support a 4-word burst read ($16\text{ bytes}$). The burst requires $1\text{ address cycle}$, $2\text{ wait cycles}$ for the initial memory access, followed by $4\text{ consecutive data cycles}$ ($1\text{ cycle per 4-byte word}$). Calculate the new effective bandwidth and the percentage speedup compared to single-word reads.
3. **Part C (Asynchronous Read):** On the asynchronous bus, the master takes $15\text{ ns}$ to set up the address lines. Memory access latency is $30\text{ ns}$. The four-phase handshake requires $4\text{ propagation and logic steps}$, each taking $8\text{ ns}$ (total handshake time $32\text{ ns}$). Latched data capture takes $10\text{ ns}$. Calculate the total time to complete a single 4-byte read and its effective bandwidth in decimal MB/s.

---

**Solution:**

**Part A: Synchronous Single-Word Read**

Total clock cycles required:

$$C_{\text{total}} = C_{\text{address}} + C_{\text{wait}} + C_{\text{data}} = 1 + 2 + 1 = 4\text{ clock cycles}$$

Total read duration at $66\text{ MHz}$ ($T_{\text{cyc}} = 15.15\text{ ns}$):

$$T_{\text{read}} = 4 \times 15.15\text{ ns} = 60.60\text{ ns}$$

Effective bus bandwidth:

$$\text{Bandwidth} = \frac{4\text{ bytes}}{60.60 \times 10^{-9}\text{ s}} \approx 66.0\text{ MB/s (decimal)}$$

Bus transfer efficiency:

$$\text{Efficiency} = \frac{C_{\text{data}}}{C_{\text{total}}} = \frac{1}{4} = 25\%$$

The bus is actively moving payload data during only $25\%$ of its operating time; $75\%$ of the time is consumed by addressing and waiting.

**Part B: Synchronous Burst Mode Read**

In burst mode, 4 words ($16\text{ bytes}$) are transferred. Total clock cycles:

$$C_{\text{burst}} = C_{\text{address}} + C_{\text{wait}} + (4 \times C_{\text{data}}) = 1 + 2 + 4 = 7\text{ clock cycles}$$

Total burst duration:

$$T_{\text{burst}} = 7 \times 15.15\text{ ns} = 106.05\text{ ns}$$

Effective bandwidth:

$$\text{Bandwidth}_{\text{burst}} = \frac{16\text{ bytes}}{106.05 \times 10^{-9}\text{ s}} \approx 150.87\text{ MB/s (decimal)}$$

Speedup:

$$\text{Speedup} = \frac{\text{Bandwidth}_{\text{burst}}}{\text{Bandwidth}_{\text{single}}} = \frac{150.87}{66.0} \approx 2.29\times\text{ (a 128.6\% improvement)}$$

By amortizing the address and wait cycles over four consecutive data transfers, the bus efficiency rises to $4/7 \approx 57.1\%$.

**Part C: Asynchronous Read**

Total time for the asynchronous transfer is the direct sum of its non-overlapping physical delays:

$$T_{\text{async}} = T_{\text{address\_setup}} + T_{\text{access}} + T_{\text{handshake}} + T_{\text{latch}}$$
$$T_{\text{async}} = 15\text{ ns} + 30\text{ ns} + 32\text{ ns} + 10\text{ ns} = 87\text{ ns}$$

Effective asynchronous bandwidth:

$$\text{Bandwidth}_{\text{async}} = \frac{4\text{ bytes}}{87 \times 10^{-9}\text{ s}} \approx 45.98\text{ MB/s (decimal)}$$

Comparing the two: The synchronous bus ($60.60\text{ ns}$, $66.0\text{ MB/s}$) is faster than the asynchronous bus ($87\text{ ns}$, $45.98\text{ MB/s}$) for single-word transfers, because the asynchronous bus must pay $32\text{ ns}$ of four-phase handshaking delays.
</ModelAnswer>

### Problem 2: Bus Arbitration Analysis: Daisy Chain vs. Round-Robin Fairness

<ModelAnswer>
**Problem:** A computer system has 4 bus masters: Master 0 (GPU), Master 1 (NVMe SSD), Master 2 (Gigabit Network), and Master 3 (CPU). Each bus transaction takes exactly $100\text{ ns}$ of bus transmission time.

1. **Part A (Daisy Chain Starvation):** The four devices are connected in a physical daisy chain in the order Master 0 $\to$ Master 1 $\to$ Master 2 $\to$ Master 3. Master 0 requires bus access $70\%$ of the total available time, and Master 1 requires bus access $25\%$ of the total time. If bus requests arrive independently, what percentage of the total bus bandwidth is left available for Master 2 and Master 3? What happens to the CPU (Master 3) if Master 0 increases its bus demand to $80\%$ and Master 1 to $25\%$?
2. **Part B (Round-Robin Bounded Waiting Time):** The system replaces daisy chaining with a centralized round-robin arbiter. Each master is granted at most one $100\text{ ns}$ transaction per turn before the arbiter advances to the next requesting master. If Master 3 asserts a bus request, what is the guaranteed worst-case waiting time until Master 3's transaction begins, assuming all other three masters are also demanding the bus?
3. **Part C (Bandwidth Allocation):** Under continuous maximum load where all four masters request the bus constantly, what fraction and percentage of total bus bandwidth does each master receive under round-robin arbitration?

---

**Solution:**

**Part A: Daisy Chain Allocation and Starvation**

In a daisy chain, upstream masters hold absolute priority over downstream masters.

- Master 0 receives first choice and consumes $70\%$ of bus bandwidth.
- The remaining bandwidth available to downstream devices is $100\% - 70\% = 30\%$.
- Master 1 consumes $25\%$ out of this remaining capacity.
- The remaining bandwidth available for Master 2 and Master 3 combined is:

$$\text{Bandwidth}_{\text{remaining}} = 30\% - 25\% = 5\%$$

Master 2 and Master 3 must share the remaining $5\%$.

If Master 0 increases its demand to $80\%$ and Master 1 requires $25\%$:

$$\text{Demand}_{\text{M0}} + \text{Demand}_{\text{M1}} = 80\% + 25\% = 105\% > 100\%$$

Master 0 takes $80\%$, Master 1 takes the remaining $20\%$ (leaving Master 1 partially starved), and **zero bandwidth ($0\%$)** reaches Master 2 and Master 3. The CPU (Master 3) is completely starved of memory access, freezing all foreground user computation.

**Part B: Round-Robin Bounded Waiting Time**

In a 4-master round-robin arbiter, after serving Master 3, the arbiter services Master 0, Master 1, and Master 2 in rotation.

The worst-case scenario occurs when Master 3 asserts its request an infinitesimal instant after the arbiter grant has already passed Master 3 and started serving Master 0.

Before Master 3 can receive another grant, each of the other three masters can execute at most one $100\text{ ns}$ transaction:

$$T_{\text{wait\_max}} = (N - 1) \times T_{\text{transaction}} = (4 - 1) \times 100\text{ ns} = 3 \times 100\text{ ns} = 300\text{ ns}$$

Master 3 is guaranteed to begin its transaction within at most $300\text{ ns}$. Starvation is mathematically impossible.

**Part C: Round-Robin Bandwidth Allocation**

When all four masters continuously request the bus, the round-robin arbiter cycles through them in strict sequence:

$$\text{Sequence}: \text{M0} \to \text{M1} \to \text{M2} \to \text{M3} \to \text{M0} \to \dots$$

Each master receives exactly one transaction per 4-transaction cycle.

$$\text{Bandwidth Share} = \frac{1}{4} = 25\%$$

Each master is guaranteed exactly $25\%$ of total bus bandwidth, providing complete fairness regardless of device priority or physical slot position.
</ModelAnswer>
