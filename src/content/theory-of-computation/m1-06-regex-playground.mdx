# Practical: Building Regex from Automata

A **regular expression** is a compact notation for a finite automaton. When you write `\d{3}-\d{4}`, the engine turns it into a machine and scans your input one character at a time to check whether it matches.

Translate the automata from this module into working regex patterns below, and test where real engines differ from textbook theory.

## From textbook notation to tool syntax

Earlier in this module you used textbook notation (`+` for union, `*` for zero or more, and whole-word matching by default). JavaScript and command-line tools add a few shorthands and one big behavioral difference:

- **`^` and `$` (anchors):** By default, a tool regex succeeds if *any substring* matches. Adding `^` (start of string) and `$` (end of string) forces the pattern to consume the entire input word, just like a finite automaton does.
- **`|` (union):** Tool syntax uses `|` for "or", because `+` is taken.
- **`*`, `+`, and `{n}` (quantifiers):** `*` means zero or more, `+` means **one or more**, and `{n}` means **exactly $n$ times**.
- **`.` and `\d` (character classes):** `.` matches any single character, `[ab]` matches either `a` or `b`, and `\d` matches any digit `0` through `9`.

<Callout tone="orange" label="Forgetting anchors (^ and $)">
  If you write `\d{3}-\d{4}` without `^` and `$`, `"1234-5678"` or `"123-45678"` will still match because `234-5678` and `123-4567` sit inside them as substrings. Always wrap full-string validation patterns in `^...$` so the tool behaves like a DFA checking the whole input.
</Callout>

## Exercise C: The ReDoS trap

This exercise shows **catastrophic backtracking** (**ReDoS**, Regular Expression Denial of Service) by example. The pattern `(a+)+$` triggers it on purpose.

Why does it blow up on `"aaaa...!"`? Look at just three `a`'s followed by `!` (`"aaa!"`): the inner `a+` and outer `+` can split three `a`'s in $2^{3-1} = 4$ ways, namely `(aaa)`, `(aa)(a)`, `(a)(aa)`, or `(a)(a)(a)`. Each way fails at `$` when it hits `!`, so a **backtracking engine** (like JavaScript's `RegExp` or Python's `re`) rewinds and tries the next split. For $n$ `a`'s, each of the $n - 1$ gaps between letters can split or stay merged, giving $2^{n-1}$ paths. At $n = 25$, that is $2^{24} = 16,777,216$ failed attempts before the engine gives up, hanging your application. Removing the nested quantifier (writing `^a+$`, which matches the exact same strings) eliminates the ambiguity immediately.

<Callout tone="sky" label="Why DFAs don't hang on ReDoS">
  Knowing automata changes how you read regex. When catastrophic backtracking takes down production, you can explain *why*: someone wrote an ambiguous nested quantifier that a backtracking NFA engine had to explore along exponentially many paths. By contrast, a DFA engine (like `ripgrep` or Go's `regexp`) tracks all active states in one pass in $O(n)$ time. If you are stuck on a backtracking engine, you can fix the bug by rewriting the pattern without nested ambiguity (`^a+$`).
</Callout>
