# How to Read a Machine

You can now describe a [language](/courses/theory-of-computation/language-of-languages#language-l) as a set, and generate one with a [grammar](/courses/theory-of-computation/grammars). The next question goes in the opposite direction: **given a string, how does a machine decide whether it belongs to the language?**

The answer is a **state diagram**. You take a drawing and a string, follow the arrows, and decide accept or reject. Module 1 writes the same machine formally as a tuple of sets and functions, but the picture comes first because the notation is easier to trust once you have traced a machine by hand.

## The Anatomy of a State Diagram

A state diagram has four ingredients.

**States** are drawn as circles. Each circle is a snapshot of the machine's memory. A finite automaton has no tape, counter or variables; its entire memory at any moment is which circle it's in.

**The initial state** (also called the **start state**) has an arrow pointing into it from nowhere. The machine always starts there, before reading any symbol.

**Accept states** (also called **final states**) are drawn as double circles. If the machine finishes reading the whole input while sitting in one of these, it answers *yes, this string is in the language*. If it ends anywhere else, the answer is *no*.

**Transitions** are arrows between states, each labeled with a symbol from the [alphabet](/courses/theory-of-computation/language-of-languages#alphabet-sigma). When the machine reads a symbol, it follows the arrow with that label out of its current state.

<Callout tone="violet" label="The machine's only job">
  Read one symbol. Follow the matching arrow. Repeat until the string runs out, then check whether the final state is an accept state.
</Callout>

## What "DFA" Means

The machine those four ingredients describe is called a **deterministic finite automaton**, or **DFA**. Each word in the name is a constraint.

- **Deterministic:** at every state, for every symbol in the [alphabet](/courses/theory-of-computation/language-of-languages#alphabet-sigma), there is *exactly one* arrow leaving. Given the current state and the next input symbol, the next state is fully decided.
- **Finite:** the machine has a finite number of states. Its memory budget is the number of circles in the diagram, with no counter, stack or scratchpad on the side.
- **Automaton:** an automatic machine. Once you hand it an input string, it runs on its own, symbol by symbol.

Put together, a DFA is a machine with a fixed number of memory slots that reacts to each input symbol in one way. Every other automaton you'll meet later in the course relaxes one of these three words.

The formal definition, a 5-tuple of sets and functions that names each ingredient precisely, comes in Module 1. Until then, the picture tells you everything you need.

## A First Example: A Parking Meter

A parking meter that opens its gate once you insert \$20 or more is a deterministic finite automaton. The states track *amount paid so far*, the alphabet is *the coins you can insert*, and the accept state is *gate open*.

This meter accepts three coins, \$5, \$10, and \$25,
and opens at any total of \$20 or more.

The states are:

- $q_0$: \$0 paid *(start)*
- $q_5$: \$5
- $q_{10}$: \$10
- $q_{15}$: \$15
- $q_\text{open}$: \$20 or more *(accept)*. Notice the three self-loops back to $q_\text{open}$: because a DFA must define a transition for every coin from every state, inserting extra coins after the gate opens simply keeps the machine in $q_\text{open}$.

Try a few sequences in the input box above. Spaces are optional, so `$5 $10 $5` and `$5$10$5` are read the same way:

- `$5 $10 $5` → \$20 → **accepted** ($q_0 \rightarrow q_5 \rightarrow q_{15} \rightarrow q_\text{open}$)
- `$10 $25` → \$35 → **accepted** ($q_0 \rightarrow q_{10} \rightarrow q_\text{open}$)
- `$5 $5` → \$10 → **rejected** ($q_0 \rightarrow q_5 \rightarrow q_{10}$, gate stays closed)

This is what designing a DFA looks like when the language has a clear counter to track. Once you decide *the running total is what I track*, every arrow in the diagram is forced. Not every language gives you an obvious counter. The next machine's states have less obvious meanings, so you'll work them out by tracing strings.

## A Machine, Read by Hand

Here is a machine over the alphabet $\{a, b\}$. Step through it before reading the explanation below.

Here is the same machine as a **transition table**. Each row says "from this state, on this symbol, go to this state":

| State | on $a$ | on $b$ |
| --- | --- | --- |
| $q_0$ (start) | $q_1$ | $q_0$ |
| $q_1$ | $q_1$ | $q_2$ |
| $q_2$ (accept) | $q_1$ | $q_0$ |

Picture and table contain the same six arrows. The picture shows you the shape; the table is what you scan when you're tracing by hand and don't want to lose your place.

Try the strings `ab`, `abb`, `b`, `bab` and `aab` before reading on, and guess what language this machine accepts.

Now trace each string in a table. Each row is one moment in time: *Read* is the symbol just consumed, and *State* is where the machine sits after consuming it.

Take the string $ab$:

| Step | Read | State |
| --- | --- | --- |
| 0 | (start) | $q_0$ |
| 1 | $a$ | $q_1$ |
| 2 | $b$ | $q_2$ |

It ends at $q_2$, an accept state. **Accepted.**

Take the string $abb$:

| Step | Read | State |
| --- | --- | --- |
| 0 | (start) | $q_0$ |
| 1 | $a$ | $q_1$ |
| 2 | $b$ | $q_2$ |
| 3 | $b$ | $q_0$ |

Notice step 2: after reading $ab$, the machine sits in the accept state $q_2$, but the string is not finished yet. It must keep going, read the final $b$, and move to $q_0$, which is not an accept state. **Rejected.**

Take the string $b$:

| Step | Read | State |
| --- | --- | --- |
| 0 | (start) | $q_0$ |
| 1 | $b$ | $q_0$ |

It ends at $q_0$, which is not an accept state. **Rejected.**

Finally, take the [empty string](/courses/theory-of-computation/language-of-languages#string-word) $\varepsilon$ (zero symbols):

| Step | Read | State |
| --- | --- | --- |
| 0 | (start) | $q_0$ |

With zero symbols left to read, the machine stops immediately in $q_0$, which is not an accept state. **Rejected.**

<Callout tone="orange" label="Two tracing traps: stopping early and forgetting ε">
  Students frequently trip on two edge cases when tracing by hand:
  - **Stopping early:** landing in an accept state partway through the input (like reaching $q_2$ at step 2 of $abb$) does *not* accept the string. You check whether you are in an accept state only after consuming the **entire** string.
  - **Forgetting $\varepsilon$:** because $\varepsilon$ has zero symbols, the machine takes zero arrows and stays at the start state. A DFA accepts $\varepsilon$ if and only if its start state is also an accept state.
</Callout>

The rule: **every accepted string ends in $ab$.**

The accepted strings ($ab$, $aab$, $bab$) all end with $a$ followed by $b$, and the rejected ones ($abb$, $b$, $\varepsilon$) don't. The machine checks exactly one thing: *did the input just end in $ab$?*

In programmer regex syntax, this language is `/ab$/`, where the slashes wrap the pattern and `$` marks the end of the string (not a dollar sign as in the parking meter above). A regex engine compiles a pattern like this into a state machine that runs exactly the way you just traced, with the same circles, arrows and accept condition.

The point here is the skill: tracing the machine symbol by symbol. The first lesson of Module 1 takes this exact machine and writes it down as a 5-tuple, with the same six arrows in formal syntax.

## What Each State Means

Each state represents a **condition the machine needs to remember** to handle future symbols.

$q_0$ means: *the last symbol I read was $b$, or I haven't read anything yet.* It isn't ready to accept, because it needs to see an $a$ first.
$q_1$ means: *the last symbol I read was $a$.* One $b$ away from accepting.
$q_2$ means: *the last two symbols I read were $ab$.* This is the accepting condition.

Whenever you design or read a state diagram, ask: *what does this state know?* The answer is always a condition on the input seen so far, and that condition is the state's meaning. Once you read machines as memory like this, designing one becomes a matter of working out which conditions the language needs you to track.

<Callout tone="orange" label="The finite memory constraint">
  A finite automaton has exactly as many memory slots as it has states. Three states means three possible conditions it can distinguish. If the language requires remembering something that grows with the input, like an exact count of $a$'s, a finite automaton can't do it. You'll prove this formally later. For now, notice that the number of states is the machine's entire memory budget.
</Callout>

## Two important notes

Before moving to Module 1, keep two rules in mind:

**Every state must have exactly one outgoing arrow per symbol.** If the alphabet is $\{a, b\}$, every state needs exactly one $a$-arrow and one $b$-arrow leaving it. A DFA that satisfies this rule everywhere is called a **complete DFA**. Unlike the shorthand diagram in the [Grammars lesson](/courses/theory-of-computation/grammars#a-regular-grammar-is-a-finite-automaton) that omitted error transitions out of `F`, turning an incomplete diagram into a valid complete DFA means routing every missing symbol to a non-accepting **trap state** (also called a **dead state** or **sink state**) that loops back to itself on every symbol in $\Sigma$. Once a string enters the trap state, it can never leave and is guaranteed to reject. By contrast, a machine where two $a$-arrows leave the same state is a different kind of machine, a nondeterministic automaton, which Module 1 covers.

**The machine cannot look ahead.** It reads left to right, one symbol at a time, with no ability to peek at what comes next or go back. Every decision is made with only the current state and the current symbol. That constraint keeps the model limited enough to analyze mathematically, while staying expressive enough to match real tools like regex engines.

## Practice: trace a transition table

Use this DFA over $\{a, b\}$ to trace `bba`, `ab`, and $\varepsilon$ by hand, then decide what language the machine accepts:

| State | on $a$ | on $b$ |
| --- | --- | --- |
| $q_0$ (start, accept) | $q_1$ | $q_0$ |
| $q_1$ | $q_1$ | $q_0$ |

<ModelAnswer>
- **`bba`:** $q_0 \xrightarrow{b} q_0 \xrightarrow{b} q_0 \xrightarrow{a} q_1$. Since $q_1$ is not an accept state, `bba` is **rejected**.
- **`ab`:** $q_0 \xrightarrow{a} q_1 \xrightarrow{b} q_0$. Since $q_0$ is an accept state, `ab` is **accepted**.
- **$\varepsilon$:** zero steps keeps you at the start state $q_0$. Because $q_0$ is an accept state, $\varepsilon$ is **accepted**.
- **Language:** every string that ends in $b$, plus $\varepsilon$ (equivalently, every string that does not end in $a$).
</ModelAnswer>
