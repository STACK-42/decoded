# Pushdown Automata

[The Limits of Finite Memory](/courses/theory-of-computation/limits-of-finite-memory#what-is-missing-is-a-stack) ended with an idea: a finite automaton fails on $a^nb^n$ because it can't count without limit, and adding one [stack](/courses/data-structures/stacks#the-interface) fixes that. A **pushdown automaton** (PDA) is exactly that machine: a finite control plus a stack that can grow as large as the input needs, where only the top is ever visible.

## The pieces

A PDA can be drawn as a flowchart. Before any step runs, the input tape holds the word followed by infinitely many blank symbols $\Delta$, the read head starts at the first letter, and the stack begins empty (full of $\Delta$). A run starts at START and moves from box to box:

- **START** is where every run begins.
- **READ** takes the next letter from the input tape and follows the edge labeled with that letter (without changing the stack). Once the word is used up, READ finds $\Delta$.
- **POP** removes the top symbol from the stack and follows the edge labeled with it (without advancing the input tape). If the stack is empty, POP finds $\Delta$ and leaves the stack empty.
- **PUSH x** puts $x$ on top of the stack (without consuming any input).
- **ACCEPT** and **REJECT** end the run. Every machine here reads $\Delta$ on the tape before moving to ACCEPT so that the whole input must be consumed.

If a READ or POP finds a symbol with no matching edge, the machine **crashes**, which rejects that path. Leaving edges out is the normal way to say "this cannot happen in a valid word".

## A PDA for $a^nb^n$

Read the $a$'s and push one $a$ for each. When the first $b$ arrives, switch to popping: every $b$ must pop one $a$. At the end, the input must be finished ($\Delta$ on the tape) at the same moment the stack is empty ($\Delta$ on the stack).

Trace two accepted words through the flowchart step by step (writing the stack top-first):
- **$\Lambda$ (empty word, $n = 0$):** `start` $\rightarrow$ `read1` finds $\Delta$ (tape is empty) $\rightarrow$ `pop2` finds $\Delta$ (stack is empty) $\rightarrow$ `accept`.
- **`aabb`:**
  1. `start` $\rightarrow$ `read1` reads first `a` $\rightarrow$ `pushA` pushes `a` (stack: `a`).
  2. Back at `read1`, reads second `a` $\rightarrow$ `pushA` pushes `a` (stack: `aa`).
  3. Back at `read1`, reads first `b` $\rightarrow$ `pop1` removes `a` (stack: `a`) $\rightarrow$ `read2`.
  4. At `read2`, reads second `b` $\rightarrow$ `pop1` removes `a` (stack: empty) $\rightarrow$ `read2`.
  5. At `read2`, finds $\Delta$ on tape $\rightarrow$ `pop2` finds $\Delta$ on stack $\rightarrow$ `accept`.

Notice why there are **two separate READ boxes** (`read1` and `read2`) instead of looping `pop1` back to `read1`: `read1` accepts $a$'s and transitions out on the first $b$, whereas `read2` has no $a$-edge at all. Once the machine starts popping $b$'s, seeing another $a$ (as in `abab`) crashes at `read2` instead of pushing again.

Step through `aaabbb` in the runner above and watch the stack fill to three $a$'s and drain back to $\Delta$. Then try words that should fail, and find where each one crashes:

- `aab`: the input ends with an $a$ still on the stack, so `pop2` finds $a$ instead of $\Delta$ and crashes.
- `abb`: the second $b$ goes to `pop1`, which tries to pop from an empty stack, finds $\Delta$ instead of $a$, and crashes.
- `ba`: a $b$ before any $a$ goes from `read1` to `pop1` and pops from the empty stack straight away.
- `abab`: `a` pushes `a`, `b` pops `a` and moves to `read2`, and the second `a` finds no $a$-edge leaving `read2` and crashes.

The stack is the counter that a finite automaton was missing. A [DFA](/courses/theory-of-computation/how-to-read-a-machine#what-dfa-means) would need a different state for each possible count of $a$'s; this machine needs only one stack symbol, pushed as many times as the input demands.

## Nondeterminism

Like an [NFA](/courses/theory-of-computation/nfa), a PDA may have several edges with the same label out of one READ or POP box. Then it accepts a word if **some** path reaches ACCEPT. The runner searches all the paths and shows one that works.

Here is a PDA for **even-length palindromes**, words like $abba$ that read the same forward and backward. The first half is pushed onto the stack; the second half must match it, popped in reverse. The machine has no way to know where the middle is, so after every letter it nondeterministically guesses between "keep pushing" and "the middle was here, start matching".

In `abba`, `read1` has two edges for `a` (`pushA` and `popA`) and two for `b` (`pushB` and `popB`). Watch how guessing works:
- **A wrong guess:** If the machine pushes `a` (stack: `a`), then on the first `b` immediately guesses the middle and jumps to `popB`, that `popB` expects `b` on top of the stack, pops `a` instead, and crashes.
- **The winning path:** Push `a` (stack: `a`), push `b` (stack: `ba`, top first), then on the third letter (`b`) guess the middle and take `popB`, which pops `b` (stack: `a`) and moves to `read2`. At `read2`, read the final `a`, go to `popA`, pop `a` (stack: empty), then `read2` finds $\Delta$ on the tape and `popEnd` finds $\Delta$ on the stack $\rightarrow$ `accept`.

Try `abab` or `aba` in the runner: for `aba`, pushing `a` leaves `a` on the stack, and on `b` neither pushing `b` (stack `ba`, too tall for one remaining `a`) nor popping `b` (stack has `a`, not `b`) can succeed. Every guess crashes somewhere.

**Practice (trace the palindrome PDA):** Trace the winning path for `baab` on the even-palindrome PDA above, listing the stack contents (top first) after each step.

<Callout tone="orange" label="Common PDA design mistakes">
  Three traps when building or tracing a PDA:
  - **`POP` removes the symbol:** `POP` is destructive, not a peek. If you still need a symbol after checking it, you have to `PUSH` it back.
  - **Forgetting a phase change:** Looping back from popping to the first `READ` box in $a^nb^n$ lets `abab` slip through. Use a second `READ` box with no $a$-edge once popping begins.
  - **Assuming DPDA = NPDA:** For finite automata, determinism and nondeterminism accept the exact same languages. For PDAs they do not.
</Callout>

<Callout tone="violet" label="Here nondeterminism adds power">
  For finite automata, NFAs and DFAs recognize the same languages. For pushdown automata that's no longer true: some [context-free languages](/courses/theory-of-computation/context-free-grammars), including the even palindromes $ww^R$, can only be recognized by a nondeterministic PDA. Reading $abba$ left to right, a prefix like $ab$ could be the whole first half (as in $abba$) or part of a longer one (as in $abbabba$); without a center marker (compare $wcw^R$, where $c$ signals "start popping" and a deterministic PDA works), a deterministic machine can't know where the first half ends.
</Callout>

## The formal definition

Other textbooks define a PDA as a 7-tuple $(Q, \Sigma, \Gamma, \delta, q_0, Z_0, F)$: states $Q$, input [alphabet](/courses/theory-of-computation/language-of-languages#alphabet-sigma) $\Sigma$, **stack alphabet** $\Gamma$ (the symbols allowed on the stack, which often includes helper markers or grammar variables beyond $\Sigma$), transition function $\delta$, start state $q_0$, **initial stack symbol** $Z_0$ (a bottom-of-stack marker placed at startup to detect an empty stack, like $\Delta$ in the flowcharts), and final states $F$.

Each transition $\delta(q, a, X) \ni (q', \gamma)$ reads an input letter $a \in \Sigma \cup \{\varepsilon\}$, pops the top symbol $X$ from the stack, moves to state $q'$, and pushes a stack string $\gamma \in \Gamma^*$ in place of $X$ ($\gamma = \varepsilon$ pops $X$ without replacing it, $\gamma = X$ leaves $X$ unchanged, and $\gamma = YX$ pushes $Y$ on top of $X$). A 7-tuple PDA accepts either by reaching a state in $F$ at the end of the input or by emptying its stack; both conventions define the exact same languages as the flowcharts above.

## Where this shows up today

<ApplicationsGrid>
  <PracticalApplication title="HTML parsing" tool="BROWSERS">
    The HTML standard describes a parser with a "stack of open elements": an opening tag pushes, a closing tag pops back to the matching element. That stack is how a browser knows which element a closing tag ends.
  </PracticalApplication>
  <PracticalApplication title="Parser generators" tool="YACC / BISON">
    The parsers that yacc and Bison generate are pushdown automata: a finite table of states plus a stack of grammar symbols, shifting input onto the stack and reducing the top of it with grammar rules.
  </PracticalApplication>
  <PracticalApplication title="The call stack" tool="EVERY PROGRAM">
    Every [function call](/courses/microprocessors/stack-and-procedures#call-and-ret) pushes a frame and every return pops one. That's why recursion handles nested structures (JSON, folders, expressions) that a loop with a fixed number of variables can't.
  </PracticalApplication>
</ApplicationsGrid>
